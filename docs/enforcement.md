# Enforcement: what actually stops a session

Prompts and hooks are not a security boundary. A session can phrase a command a hook doesn't recognise, and a hook's own files live in the repo it is working on. So the kit relies on boundaries outside the session, and uses its hooks as defence in depth.

| Layer | Enforces | Set up by |
|---|---|---|
| **GitHub ruleset on the base branch** | No direct push, no force-push, no deletion; required status checks before merge | The owner, once per repo |
| **Cloud environments per role** | Ticket sessions: no cloud, account, deploy or payment credentials, `WORKFLOW_ROLE=ticket`. The conductor: `WORKFLOW_ROLE=conductor` and only the release credentials the owner chooses | The owner; shared by repos whose environment setup scripts match, often blank (§2) |
| **CODEOWNERS on protected paths** | Changes to the kit and its hooks (`.claude/`), CI config (`.github/workflows/`) and CODEOWNERS itself ask for the owner's review | `setup-workflow` writes it; the ruleset can require that review only when agents have their own GitHub identity (§1) |
| **The guard hook** | The never-list, protected paths, skip markers, sensitive posts, the agents' marker on posts | The kit |
| **Instructions** | Everything else | The kit |

## 1. The ruleset (GitHub → the repo → Settings → Rules → Rulesets → New branch ruleset)

The `upgrade-setup` skill's "Protect `main`" sets this up.

- **On the owner's own computer,** with `gh` signed in as the repository's admin and no ruleset on the base branch yet, the kit makes this ruleset itself after one confirmation, with `gh api` and the requests `workflow protection --protect` builds.
- **The ruleset it makes:** a branch ruleset named "Protect <base> (pairnexus-workflow)", **Active**, with an empty bypass list, on the base branch (`~DEFAULT_BRANCH` when it is the default). Its rules: Restrict deletions, Block force pushes, Require a pull request before merging (required approvals 0, Code Owners off) and, for the checks the owner ticks, Require status checks to pass with "up to date" on.
- **The merge settings:** it then turns on "Allow merge commits" and "Allow auto-merge".
- **The required checks:** the kit adds the required checks once CI has run on the base branch: the skill's "Require these checks", offered by `workflow doctor` (through `check-setup` and the conductor's pre-flight) or when asked. It shows the checks that ran, passing ones ticked, adds the ticked ones to the ruleset protecting the base branch with "up to date" on, or left as it is beside a merge queue (a `PUT` with `gh api` after one confirmation on the owner's own computer, the clicks elsewhere), reads them back, and lists them in `ci.required_checks` in a small pull request. Checks are only ever added, never removed. In solo mode it waits for the pull request that leaves it.
- **The guard** asks before the ruleset is created; the merge settings are not asked. Adding checks to the ruleset is asked too, and refused in solo mode.
- **Everyone else gets the guided clicks below:** cloud sessions, a missing or signed-out `gh`, and a ruleset already on the base branch that doesn't protect it. The clicks stay the fallback whenever a step fails. The kit never edits an existing ruleset in solo mode.

- **Target:** the profile's `project.base_branch`, normally the default branch ("Include default branch"); if they differ, target the base branch by name.
- **Rules:** Restrict deletions; Block force pushes; Require a pull request before merging (required approvals **0**, so unattended runs can merge: with more, the conductor recommends `merge.mode: owner` and runs stop at "ready for review"; "Require review from Code Owners": see below); Require status checks to pass (add the profile's `ci.required_checks`, and tick "Require branches to be up to date", which the API calls `strict_required_status_checks_policy`, unless the ruleset has a merge queue, which meets it: "Use a merge queue" turns it off).
- **Bypass list:** empty. Sessions act through the owner's GitHub account, so whatever the owner may bypass, a session may too.
- **Merge settings:** keep "Allow merge commits" on and "Require linear history" off: sessions and the conductor merge with a merge commit.
- **Enforcement status: Active.** A ruleset left "Disabled" or "Evaluate" enforces nothing.
- **Allow auto-merge:** Settings → General → Pull Requests → "Allow auto-merge", for runs whose charter says `merge.mode: auto-merge`. The merge mode is chosen per run, in the charter (`charter.md` §2), not in the profile.

**"Require review from Code Owners": leave it off while sessions act under the owner's GitHub account** (the usual setup: the GitHub connector and `gh` both use the owner's token). Every PR a session opens is then the owner's own, and GitHub never lets an author approve their own PR, so a PR touching a CODEOWNERS path could never merge. With it off, CODEOWNERS still requests the owner's review on those PRs, and the protected paths stay protected by the guard, by the ticket environment having no credentials, and by such PRs going to the owner (a ticket that changes one is an owner task, never a build ticket).

Turn it on when agents use their own GitHub identity (a bot account or a GitHub App): then the owner is a different person from the PR's author, and their approval is what merges a change to a protected path.

"Require branches to be up to date" matters more than it looks: without it, two PRs that are each green against an older base can both merge and break the base together. If the owner leaves it off with no merge queue on the base branch, the conductor's pre-flight raises it as a safety gap: a merge queue meets it instead, since it tests each pull request against the latest base before merging (`docs/protection.md`, "The merge queue"). Every merge in a run still runs on `workflow merge-check`, which never says `ready` for a branch that isn't level with the base (flow §4.3), unless a merge queue meets it: then `ready` means ready to queue.

Rulesets and branch protection on **private** repositories need a paid GitHub plan for the organisation (Team or above). Without one, the guard hook and instructions are the only line, and the charter's pre-flight says so.

A charter waiver for a killed check can't override a ruleset's required check. Where a check is known to be killed by its runners, either fix the job first, or leave it out of the ruleset's required checks for the run (the conductor's pre-flight then shows the difference from `ci.required_checks` as a gap for the owner to accept) and use `merge.mode: session`, where the session reads that check's log for a killed marker and posts the local evidence before merging. Never combine a waiver with GitHub auto-merge: it can't tell killed from failed.

## 2. The environments (claude.ai/code → the environment menu → add, or Edit)

Two environments, named in the profile (`run.ticket_environment`, `run.conductor_environment`). The kit's README has the clicks: https://github.com/medTech-group/pairnexus-workflow#step-5-create-the-two-claude-environments.

**The names must match exactly.** An environment's id belongs to the owner's Claude account, so the repo records names instead. The conductor lists the account's environments, takes the one named `run.ticket_environment`, and starts every ticket session in it. With no environment of that name it stops in pre-flight and starts nothing. A ticket session in the wrong environment would have whatever credentials that environment holds, and no `WORKFLOW_ROLE`.

**Setup script: machine tools only.** An environment's setup script runs before the repository is there and is cached for later sessions, so it holds only machine-level tools the cloud image lacks (the profile's `run.environment_setup`; usually nothing). A script that reads the repository's files fails, and then no session in that environment starts. The project's own dependencies are `commands.setup`, which the kit's SessionStart hook runs in each cloud session, from the fresh clone, whenever `commands.setup_check` fails, and reports in the session's context ("Project setup … FAILED" when it does). So an environment holds nothing of one project, and repos whose setup scripts match can share a pair; a conductor that releases holds that project's release secrets, and gets its own.

**Ticket sessions**
- **No secrets**: no AWS keys, no Auth0, Firebase or payment credentials, no deploy tokens.
- **Environment variable:** `WORKFLOW_ROLE=ticket`.
- **Network:** what the builds and tests need (package registries, container images).
- **Setup script:** the profile's `run.environment_setup`, usually blank.

**The conductor**
- **Environment variable:** `WORKFLOW_ROLE=conductor`, so the guard denies (rather than asks a person) and allows the release steps.
- **Setup script:** the same as the ticket sessions'. The conductor's own fixes run the project's tests, and the kit installs the project's dependencies at session start as for a ticket session.
- **Secrets:** only what the charter's release steps need, if the owner wants releases unattended.

The conductor checks its own `WORKFLOW_ROLE` in pre-flight, and passes the ticket environment's id and the profile's `run.permission_mode` (`auto` recommended; a mode that prompts would stall an unattended session) to `create_session`.

The guard also recognises ticket sessions by their branch (`run.ticket_branch`) when `WORKFLOW_ROLE` isn't set. That fallback is a convenience, not a boundary: a session can change its branch (the guard refuses switching away from the pattern, but only the environment variable can't be changed from inside). Under `code_writers = "ticket"` it doesn't apply: a session that would be a ticket session only by its branch, or by a `WORKFLOW_ROLE` that isn't a role, gets an attended session's rules in full, so it may write protected paths but not code (§4, "Who writes code").

## 4. What the guard does and doesn't catch

**The tools the guard sees:** `Bash`, `Monitor`, `PowerShell`, the file-editing tools (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`) and the GitHub MCP tools (`mcp__…github…`, with a capital G or H or not). These are its hook's matcher, in a vendored project's settings and in the plugin's hooks file alike (`GUARD_MATCHER` in `scripts/workflow/vendor.py`); any other tool never reaches it.
- `Monitor` runs a shell command as Bash does, so its `command` is checked exactly as a Bash command, in every role: the same parse, allow-lists and deny-lists (a ticket session's `gh run watch` or `gh pr checks --watch` passes; a push or a deploy through it is refused or asked as through Bash). A `Monitor` with `ws` and no command (a WebSocket watch) runs nothing, and is allowed.
- `PowerShell`: the guard can't read PowerShell, and never tries to parse it. Ticket and conductor sessions are refused it ("the guard can't read PowerShell; use Bash"). An attended session gets the can't-decide rule (below) on the command's text: a push or a merge (`git … push`, `gh … pr … merge`, a backtick line continuation joined first) is asked, and refused in solo mode or where nobody is asked; anything else is left alone. The command name and its words are matched in any case, as PowerShell runs them, but in order (`git` then `push`): a program started with its arguments named first (`Start-Process -ArgumentList push -FilePath git`) isn't seen.
- Where nobody is asked, the refusal for a `Monitor` or `PowerShell` command gives the command itself to run by hand, as for Bash.

**Release gate (item 10):** the release gate runs this step at every release, after the ruleset's refusal (the kit's own `release-gate` skill, from #36's ticket #92). It compares Claude Code's tools reference with the list above. A tool that runs commands or programs and is missing from the list above is a finding that fails the gate: it is added to the guard's matcher and checks in a fix release. Any other missing tool is a note in the gate's report. A test keeps the list above the same as the matcher, in a vendored project's settings and in the plugin's hooks file. So comparing with the list is comparing with the guard.

It reads each command the way a shell would, well enough to catch a well-meaning session's mistakes and the obvious tricks:
- operators and subshells wherever they sit (`;(`, `&&(`, `$(…)`, backticks, `<(…)`, function bodies);
- heredocs (scanned when they feed a shell, or when their delimiter can't be read);
- the shell's working directory, from the hook event and through `cd`/`pushd`;
- wrappers (`sudo`, `env`, `timeout`, `xargs`, `script -c` …), and a `git` or `gh` anywhere in a command's words;
- file-descriptor redirects (`2>&1` is a redirect, not an argument).

**In ticket sessions, by allow-list:**
- `git push` may update only the session's own ticket branch: no tags, no other branches, and a bare push only when the upstream has the same name;
- `gh` may run only the PR, issue, run and read subcommands a ticket needs, in the profile's repository alone (`-R`/`--repo` or a pull request or issue URL naming another, or `GH_REPO`, `GH_HOST` and gh's token variables set, are refused), never with a function's or script's parameters (`"$@"`, `$1`; text that mentions one goes in a quoted heredoc, `-m "$(cat <<'EOF' … EOF)"`, or a file with `-F`/`--body-file`), and never printing the token (`gh auth status --show-token`);
- `gh api` writes may touch only issues, comments, labels and pull requests of the profile's repo, and never GitHub's GraphQL API (auto-merge, comments and reads go through the GitHub MCP tools or REST: the shell can assemble a GraphQL query in more ways than the guard can follow); a ticket session merges, or arms auto-merge on, only its own pull request, and tells it by its head (#87). The ruleset still decides what may merge into the base branch, and conductor and attended sessions merge as before:
  - **A merge is pinned** to the head commit of the checked-out ticket branch (a branch matching `run.ticket_branch`, at `git rev-parse HEAD`), in the field GitHub checks: `gh pr merge <n> --match-head-commit <sha>`, the REST merge's `-f sha=<sha>` (`gh api -X PUT repos/<repo>/pulls/<n>/merge`), or `merge_pull_request`'s `expectedHeadSha` (a `sha` given as well must match too; on its own it doesn't count, since the tool doesn't send it). The pin is the full sha, written out. Every value counts: a repeated `sha` or `--match-head-commit` must match each time.
  - **Refused, saying how to pin it:** an unpinned merge, a pin to any other commit (an empty one beside it included: gh sends the last), a REST merge with an `--input` body or an `@file` field (gh then sends a body the guard doesn't read), a merge or arm, or any other `gh api` call (a read included), with a word the shell expands into other words outside quotes (a variable, a substitution, a glob, a brace list or a leading tilde, or a quoted array such as `"${A[@]}"`: a merge path or `-X PUT` can hide in any of them; the guard's lexer marks such words, and quoted text is fine; a command another shell reads, through `eval`, `sh -c` or a heredoc, is read by its text when the outer shell may have expanded it first) or that `xargs` feeds more words, a checkout that isn't on a ticket branch, and a `merge_pull_request` naming another repository. When the pull request's head was updated on GitHub, the refusal says to `git pull` first. `gh pr merge`'s words are read as gh reads them: a `--subject`, `--body` or `--author-email` value is text, never a flag, and only `--disable-auto` itself is a disarm.
  - **Arming auto-merge** with `gh pr merge --auto` is pinned the same way. `enable_pr_auto_merge` and the session route `PUT repos/<repo>/pulls/<n>/ccr/auto_merge` take no pin GitHub is known to check, so the guard always reads the pull request's head back (`gh api repos/<repo>/pulls/<n>`, from the hook): it must be the ticket branch, in this repository, at its local head. When it can't be read, the arm is refused, naming the pinned `gh pr merge --auto` and the conductor.
  - **Adding it to a merge queue** goes through one route, `gh api -X PUT repos/<repo>/pulls/<n>/merge-async -f merge_action=merge_queue -f sha=<sha>` (#244), pinned the same way: `sha` must be the ticket branch's head, written out in full. The rules every role shares are below.
  - **Disarming** (`gh pr merge <n> --disable-auto` on its own, `disable_pr_auto_merge`, `DELETE …/ccr/auto_merge`) needs no pin.
  - **What it doesn't prove:** the check reads the checkout, not the session's history. A session that checks out another ticket's branch, or resets its own to another pull request's head, can then pin to that head. It is a seatbelt against a wrong pull request number, not a lock; the review panel's record and `workflow merge-check` are what a merge rests on;
- git that runs a program the guard can't see is refused (`rebase --exec`, `bisect run`, `submodule foreach`, `filter-branch`, `difftool`, `mergetool`, editor and diff-driver settings or variables other than a no-op `GIT_EDITOR=true`), and `git diff|log --output`, `format-patch -o`, `archive -o` and `bundle create` count as writes (under `git -C` too);
- `git config` may not set aliases, push settings, `core.*` hooks, editors, ssh commands, credentials or includes; `GIT_CONFIG*`/`GIT_SSH*`/`GIT_DIR` assignments and `--config-env` are refused.

**In every role** it denies (asks, in attended sessions):
- pushes to the base branch in any form it can parse (refspecs, `HEAD`, `@`, abbreviated options, `send-pack`, `git-push`), force-pushes, deletes, `--mirror`, `--all`;
- `gh pr merge --admin`;
- adding a pull request to a merge queue (`PUT repos/<repo>/pulls/<n>/merge-async`, #244) other than with `-f merge_action=merge_queue` and a `sha`. The path is read by its last part, however it is spelled (a full URL, `%`-escapes, `//`, `./`, a start the shell fills in such as `repos/$REPO/…`), a last part after `pulls/<n>/` that the shell or gh fills in (`$M`, `{branch}`) or a glob counts unless the call sends the merge's `merge_method` or update-branch's `expected_head_sha`, and a path the shell fills in from start to last part (`"$URL"`) counts too when the call names a `merge_action`, PUTs a `sha` with only `merge-async`'s fields, or sends an `--input` body that names `merge_action` or `sha` or can't be read. GitHub takes the route only as a PUT, so a literal `POST`, `PATCH` or `DELETE` is left alone, unless xargs or a word the shell fills in may add a `-X PUT`: one outside a value, a filled-in path word with another word left to be the path, or an unquoted path that may split when the call names `merge_action` or `sha`. A filled-in route with the merge's or update-branch's own fields, or other fields, is left alone in conductor and attended sessions: it can't be told from those routes, and those sessions may merge through the REST merge anyway (ticket sessions' allow-list refuses any filled-in path):
  - `bypass_rules` in any form (`-f`, `-F`, or an `--input` body: a file, a heredoc, or a `cat`, `echo` or `printf` piped in; as a JSON key, escapes read), since it merges past the ruleset as `--admin` does; as a field it is refused on any `gh api` write, whatever the path (`@file` fields such as a comment's `body` aren't searched);
  - any `merge_action` but `merge_queue`, a missing one included: GitHub reads none as `default`, which merges directly when no queue is required, and `direct_merge` always does;
  - no `sha`, or one that isn't a commit: a ticket session's must be its ticket branch's head (above); anyone else's must be a full sha, or one the shell fills in (`-f sha="$SHA"`), never `-F sha=null`;
  - what the guard can't read: an `--input` body or `@file` field (refused after it is searched for `bypass_rules`), a query string or `#` on the path, a field name that isn't a plain name, words that `xargs`, `eval`, `sh -c` or an unquoted expansion add, and a quoted expansion anywhere but a field's or a flag's value or the path (`"$E"` can be `--field=bypass_rules=true`); a path whose last part the shell fills in (`pulls/12/$M`, not `pulls/comments/$ID`) counts as `merge-async`, and a path the shell fills in whole (`"$P"`) is refused beside a word that may be a flag of its own;
  - in attended sessions, a `curl` PUT to `merge-async` too (a URL names it, whatever its host or its dot segments, or a GitHub API URL's part after `pulls/<n>/` is filled in by the shell or curl, or a `-K` config names it, or is stdin (`-`, `/dev/stdin`, any path that resolves under `/dev/` or `/proc/`, `/dev/null` as written aside) or a name the shell fills in, or a missing file when the command names no URL; a curl whose every method is a literal other one, with no `--next` and no config, is left alone), unless it sends one JSON body (`-d`, `--data*` or `--json`, inline or `@file`; not with `-G`, `--url-query` or a query string) with `"merge_action": "merge_queue"`, a `"sha"`, no `bypass_rules` (escapes read) and no key given twice;
- rewriting, renaming or merging into the base branch, its protection, its rulesets or the default branch through the API.

In attended sessions the guard doesn't stop changes to protected paths: the person sees them in the pull request, which is theirs to merge.

**In solo mode** (`ruleset = false` in the profile's `[project]`, attended sessions only), nothing on GitHub stops a push to the base branch, and an ask may never reach the person (in `bypassPermissions` mode, or after an "allow" clicked by mistake). So the guard **refuses** (denies, never asks) every git push that touches the base branch:
- a push to it: by name, `HEAD`, `@` or a refspec, a bare push whose upstream is the base branch, and a push from the base branch itself (a `git checkout` or `git switch` earlier in the same command counts);
- a force-push or deletion of it (`-f`, `--force`, `--force-with-lease`, `--force-if-includes`, `+main`, `:main`, `-d`, `--delete`);
- `--mirror`, `--all` (and `--branches`), `--prune` with no branch named, a bare `:` refspec, `send-pack` without refs, and the settings that make every push a mirror or send it elsewhere: writing `remote.*.mirror`, `remote.pushDefault`, `remote.*.skipDefaultUpdate`, `remote.*.push` or a `push.default` other than `simple`, `current` or `nothing`, `git remote add --mirror`, and any push setting given to a push with `-c` or `--config-env`, or read into it with `-c include.path`, and writing a git alias that pushes (unsetting a setting is never refused);
- a bare push (no branch named) that the settings already on disk send to the base branch, for the remote git would pick: `push.default = matching`, the remote's `mirror` or its `push` refspecs naming the base branch (or ones it can't tell), or `push.default = upstream` with the branch merging into the base branch;
- a push whose destination it can't tell, which counts as the base branch: a variable, `@` or `HEAD` where the branch is unknown, a glob, a brace list, a detached HEAD, a directory it can't follow, `--git-dir` or `--work-tree`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_CONFIG…`, `HOME` or `XDG_CONFIG_HOME` set in the command, `--stdin`, branches given by `xargs`, and an alias that pushes (a git alias given with `-c` or set in the config, followed through other aliases, one that may come from config the guard can't read, or a shell alias defined in the command). The refusal says to push the branch by name.

It also refuses what changes the base branch through GitHub rather than git, so there is no side door:
- `gh pr merge --admin`, which merges past the base branch's required checks;
- changing the default branch (`gh repo edit --default-branch`, a `PATCH` of the repository with `default_branch`) and renaming the base branch (`POST …/branches/main/rename`);
- writing the base branch's protection (`…/branches/main/protection` and everything under it), and a ruleset's `PUT`, `PATCH` or `DELETE` (the repository's or the organisation's `…/rulesets/<id>`);
- updating or deleting the base branch's ref (`…/git/refs/heads/main`), merging into it through the merges API, and writing a file to it through the contents API (with no `branch`, that's the default branch);
- the same through `gh api`, `curl` (`-X`/`--request`, or the method its data or upload implies), a GraphQL mutation (`updateRef`, `deleteRef`, `mergeBranch`, `createCommitOnBranch`, the branch-protection-rule mutations, `updateRepositoryRuleset`, `deleteRepositoryRuleset`, looked for in the command and the files it reads), and the GitHub MCP tools (`push_files`, `create_or_update_file` and `delete_file` on the base branch or with none named, a ref or branch tool naming it, a protection tool for it, a ruleset tool other than creating one, and a repository update with `default_branch`). The guard reads these as gh and curl send them: every URL curl is given (and `--next`), curl's abbreviated options, dot segments and percent-encoding in a path, every value a field may take (a repeated `-f`, `-F name=@file`, an `--input` body, a JSON body's keys, duplicates and escapes included). What it can't read counts as the base branch: a path, URL, method or field name the shell fills in (a path under a repository's issues, pull requests and the like, or outside `repos/`, `orgs/` and `repositories/`, excepted, unless a ruleset, protection, branch, ref, merge or contents part follows), a curl host the shell fills in before GitHub's API paths, a call fed by `xargs`, a body file not there yet, a curl config file (`-K`) that names GitHub or can't be read, `--variable` and `--expand-…`, a curl URL with `{…}` or `[…]` (which curl expands), a gh alias that runs a shell command, and an MCP ref or branch tool with no name it can read. Calls to another repository are left as they were. A gh alias is followed (from `gh alias set` in the command, or gh's `config.yml`), and setting one that may merge with `--admin`, change the default branch or call the API is refused. For an MCP tool, the refusal gives the `gh` command that does the same by hand.

Not seen: other HTTP clients (`wget`, `httpie`, a script's own requests), a `.curlrc` or `CURL_HOME`, a gh extension's own calls, and a GraphQL query whose mutation name the shell assembles (a query in a variable is looked for in the whole command and the files it reads).

*Creating* a ruleset (a `POST` to `…/rulesets`, the `createRepositoryRuleset` mutation, an MCP tool that creates one) is still asked: it is how a project leaves solo mode. A `curl` that creates one, which attended sessions aren't asked about outside solo mode, is asked too. The repository's merge settings (`allow_auto_merge` and the like) are neither asked nor refused because of solo mode.

Every part of the command is read for these, so an ask earlier in it (a deploy command, a feature branch's force-push) never hides a refusal later on.

Force-pushing, deleting or pruning a named feature branch (`git push -f origin my-branch`, `git push origin --delete my-branch`, `git push --prune origin my-branch`) is still asked, since the force options are read with their destinations; everything else is unchanged.

The refusal says, in plain words (`main` here stands for the profile's `project.base_branch`, which the refusal names), that this would change the base branch and that the kit doesn't allow it without GitHub's protection; for someone *new to building* (and when the experience is unknown), one line on what the base branch is; the exact command to run in the person's own terminal if they mean it (a URL's password, an `Authorization` header and a `…TOKEN=` value masked, and a command over 400 characters not repeated); and an instruction to offer "Protect `main`" as a choice, with "Not now". The wording follows the person's experience (`WORKFLOW_EXPERIENCE`, then `.workflow/experience`, then `project.experience`); what is refused never does.

What still protects the base branch in solo mode is only this refusal, and the guard's other limits below apply to it: it can't see a script that pushes, or a program's own network calls. When the guard runs out of time in solo mode, the command is refused, as in ticket sessions; when the guard itself fails, an attended session's hook reports the error and doesn't decide, so that command isn't refused. Settings written in the same command by other means than `git config` (a redirect or `cp` into `.git/config`, an editor) are read only once they are on disk, by the next push; a command run through a tool the guard doesn't read as a wrapper (`parallel`) isn't seen; and an alias whose text hides `push` with quoting (`pu\sh`) isn't read as one. A switch of branch earlier in the command (`git checkout`, `git switch`, `git symbolic-ref HEAD`, or an alias that may run one) is followed: the push then counts from the branch it leaves, or as can't-tell. The person can still push from their own terminal, which the guard never sees. Protecting `main` with a ruleset (§1) is the lasting fix, after which `ruleset = true` takes the project out of solo mode. Ticket and conductor sessions are unchanged: they already deny all of this, in solo mode or not. With `ruleset = true`, or no setting, attended sessions are asked as before.

**Where nobody is asked.** In an attended session the guard's ask is no safeguard where nobody is asked: in a mode that never asks, it would go through unseen or not at all, and the ruleset is what protects `main` (§1). So the guard reads the `permission_mode` Claude Code sends with every tool call (a subagent's too, and a mode switched mid-session with Shift+Tab is followed call by call), and where nobody is asked it refuses what it would have asked:

| Permission mode | The guard's `ask` | The guard's `deny` |
|---|---|---|
| `default` | prompts | refused |
| `acceptEdits` | prompts | refused |
| `auto` | prompts | refused |
| `plan` | prompts | refused |
| `bypassPermissions` | refused, with the guard's reason | refused |
| `dontAsk` | refused, with the guard's reason | refused |
| any other value | refused, with the guard's reason, which names the value | refused |
| none sent (an older Claude Code) | prompts | refused |
| headless `claude -p` runs | refused by Claude Code, which has nobody to ask | refused |

Every ask the guard makes is covered, attended and solo mode's alike (a base-branch push, a force-push, a deploy command, `gh pr merge --admin`, a GitHub MCP write, a feature branch's force-push or delete, creating a ruleset). The refusal keeps the ask's reason and adds that the kit would have asked, that nobody is asked in this mode (named), to switch the permission mode (Shift+Tab, or the mode selector) to be asked, and how to do it by hand: the command itself, to run in your own terminal, or for a GitHub MCP tool, on GitHub. A refusal for text matching the profile's sensitive patterns says to remove the text instead; and when a command, a file it reads or posts, or a tool's input holds such text, whatever was asked, the refusal never repeats it, and says to do it by hand without that text. A mode the kit doesn't know counts as one that never asks, and its refusal names it, so you can tell the kit's maintainers about it. The guard's modes are listed in `scripts/workflow/modes.py`, written in Python 3.7 syntax with no imports for the old-Python fallback; that fallback and the guard's own can't-decide fallback (#53) read it too; the hook command's fallback without Python (#56, `scripts/workflow/fallback.sh`) keeps a copy of the list, which a test checks against it. Denies, and what the guard leaves alone, are the same in every mode, and ticket and conductor sessions, which deny already, are unchanged.

**In ticket sessions it also denies:**
- the profile's deploy commands, however they're run (directly, through a shell, piped, `env -C`, `find -exec`);
- writes to protected paths, `.git/config` and `.git/hooks/**`, by Edit/Write, by the shell's writers (redirects, `cp`/`mv`/`install`/`rsync`/`ln` destinations, `rm`, `sed -i`, `perl -pi`, `dd`, `tee`, `mkdir`, `curl -o`, `wget -O`, `find -delete` and `find -exec` over a tree holding one (a plain `find DIR -name GLOB … -delete` or `-exec … {} +` that the guard can read exactly is checked by name against the files there, directories holding protected paths and links to them included; anything else is a write into the whole tree), commands run by `xargs` (their targets are what the producer names exactly, else they can't be seen), a tree checked on disk for a protected path a pattern matches anywhere (`**/.env`, up to 50,000 entries), `git rm`/`mv`/`checkout`/`restore`, archives and patches that touch them, deleting a parent directory, globs and brace lists that expand to them, symlinks resolved), or through GitHub's file tools;
- a new skip or focus marker in a test file (`conftest.py` included). An editing script is read by its tool's grammar: the text sed's `a`, `i` and `c` write counts as added, an address or a regex only finds, vim's and ed's `s` ends at the end of its line, perl's and awk's strings are text they write, a sed script on standard input is read from the heredoc or file that gives it, and a patch's lines are read as they stand. A sed, perl or awk script the guard can't read counts every marker in it as added. Scripts over 1 MB together, patches over 4 MB together, and a Write over a test file of more than 4 MB are refused rather than read in part;
- switching to a branch outside the pattern when the role comes only from the branch name (with `code_writers` other than `"ticket"`: under `"ticket"` such a session isn't a ticket session, below).

A GitHub post (MCP or `gh`, including heredoc bodies and `--body-file`/`--input` files) matching the profile's sensitive patterns is refused in every role.

In ticket and conductor sessions, a post that creates text (an issue, PR, comment or review, or a new body for one, through `gh issue|pr create|comment|edit|close|reopen`, `gh api` to issues, pull requests, reviews and commit comments with a `body` field, or with `--input` JSON that carries a `body` or `comment` or can't be read, the conductor's GraphQL mutations that post, or the GitHub MCP tools that do) is refused unless it carries `<!-- workflow:agent -->`: the marker that tells agents' posts from the owner's own words (`charter.md` §4). A GraphQL query sent with `--input` (a file or stdin) is read from its JSON's `query`, and a mutation that may carry a body (`updateIssue`, `updatePullRequest` …) counts only when its arguments, or the variables they take, hold one; a `body` in what it asks back doesn't count. Labels, assignees, state changes (`--input` JSON such as `{"state": "closed"}` that can be read), `gh issue|pr comment --delete-last` and merges aren't posts. Attended sessions aren't asked.

The marker is looked for in the command's texts as a whole (the command, its heredocs, its body and `--input` files, what it reads with `cat` or `<`), not in each post separately: a command that posts twice passes when either text carries it. It is a seatbelt against forgetting the marker, not proof that each post is an agent's. A conductor's GraphQL post assembled by the shell (a field name from a variable, brace expansion, `xargs`) can get past it; the conductor is trusted not to hide its posts, and ticket sessions use no GraphQL at all.

Writing into, removing or searching a directory above the project counts as doing so to all of it. Git is found behind wrappers, as in ticket sessions. - **`git commit`** (#389) in the project's own repository (the project, or any worktree of it, `--work-tree` elsewhere included): refused when the files it would carry include a code path, so code written in a way the guard couldn't see (`python3 -c …`) is caught before it is committed. What it carries is what is staged, plus the tracked files changed in the working tree with `-a` (or `-p`, `--interactive`, which choose among them), or what a pathspec names (on the command line, brace lists expanded, or by `--pathspec-from-file`; a pathspec alone commits only what it names, unless `-i` adds the staged files to it); renames count as both their paths. **A commit finishing a merge** (`git commit` while one is in progress, or `git merge --continue`; #391) carries only the merge's own changes, read as a pushed merge commit is (below): for a merge of two parents, against those parents merged again (`--diff-merges=remerge`), so what git merges cleanly isn't counted, whatever lines or renames it spans, while a conflict resolved in a code path (taking one parent's version included, as `-s ours` and `-X ours` do) or a change neither parent has is; a merge of more parents, which git doesn't merge again, as `git diff-tree --cc -U0` reads it. The working tree's changes that `-a` or a pathspec adds count as they are. The guard writes the merge commit from a copy of the index into a temporary object store, so the repository is left as it was; a file still unmerged in the index counts by its version in the working tree when `-a` takes it (git commits it in no other way). The guard merges again in a temporary object store of its own, with no clean filter (`merge.renormalize` off) and no hook (its reads set `core.hooksPath` to nothing), reading the patch's file headers, so a conflict that changed no content (a binary file, a rename against a deletion) counts too; when git's config names a merge driver (`merge.<name>.driver`, in any file git reads, the global one included), which merging again would run, it doesn't merge again. A merge made with other merge settings or options than the repository's own (`-X patience`, `--no-renames`, another tool), or in a repository that sets `merge.renormalize` (which the guard turns off, since renormalizing runs filter programs), may count files it took cleanly as the merge's own change. Merging again takes time: a merge that changes thousands of large files on both parents can take longer than a git read may (5 seconds), and is then asked, as any read it can't finish. When it can't read the merge's own changes (that, or a git read that fails or takes too long), the commit is a commit it can't tell about (below) when what is staged differs from a parent in a code path, and a push of a merge of two parents is a push it can't tell about. So bringing a pull request up to date with its base goes through. Finishing a cherry-pick (everything staged counts), a rebase or `git am` (`git commit`, or `--continue`, `git am --resolved`) is judged as any commit; finishing a revert, by the revert rule (below). The guard's own reads run no fsmonitor. A `--dry-run` (and `--short`, `--porcelain`, `--long` and `-z`, which imply it, and `-h` or `--help`), and a commit in another repository already there (another clone, or one nested in the project) or in a directory the guard can't follow, are left alone (the push rule is the next check).
- **When it can't tell** what a commit carries, an attended session (including one that is a ticket session only by its branch or a mistyped role) is asked, naming what it couldn't read; in a permission mode that never asks, that ask is a refusal. That is when a git read fails while the guard runs (or it can't read the project's own repository), which includes a commit from a directory that isn't in a repository yet, wherever it is (git commits there only once the command makes it one, however it spells the `.git`), or the command sets `GIT_DIR`, `GIT_WORK_TREE` or `GIT_COMMON_DIR` for it (wherever it runs), or `GIT_INDEX_FILE` or `GIT_OBJECT_DIRECTORY` in the project's repository, or runs it in a directory that doesn't exist yet (one the command makes first, a link among them, wherever it is), or where an earlier part of the command adds a worktree (`git worktree add`) or makes a repository (`git init`, `git clone` or `gh repo clone`; not an init whose `GIT_DIR` or `--git-dir` puts it elsewhere), there or in a folder holding it with no repository already nearer, since what git would commit into isn't on disk yet; or, for a commit it wouldn't refuse anyway (it is judged where it is now, and a refusal stands), where a later part does so (it may run first: the commit in the background, in a pipeline or a loop), or when the command names a `.git` anywhere in its text, in any case, quoted or not (`.g"it"`, `.g\it`), even only to read it (the guard doesn't tell reads from writes, and a `.git` written, linked, moved or removed can send the commit anywhere; `.gitignore`, `.github` and `demo.git` aren't one); and when a pathspec is one it can't read (a word the shell expands, a brace sequence or a list of more than 64, a glob where git reads pathspecs literally, the names `xargs` or `find -exec` gives it, a pathspec file that isn't a plain file it can read, holds quoted lines, or is written earlier in the command or by the commit's own redirect) and the changes the commit could carry, staged or not, include a code path (none: it goes through). The conductor, which the guard never asks for, is refused, naming what it couldn't read. Another part of the command that is refused still is; one that is asked is asked together with it.
- **`git push`** (#390) to `project.repo`, from any directory (another clone, a repository nested in the project, a worktree): refused when the commits it would send carry a code path, so code committed where the commit rule doesn't look (another clone, plumbing, an alias, `rebase --exec`) is caught before it reaches GitHub. The refusal names the commit, the path and the repository.
  - **What it sends:** what its refs reach (a refspec's source, `tag <name>`, `HEAD` for a bare push; every branch for `--all`, `:`, `push.default = matching`; every ref for `--mirror` or a remote's `mirror` setting; every tag for `--tags`, which alone sends only tags; nothing more for `--follow-tags`, whose tags are on commits the push sends; every ref a `refs/…*` pattern could match; a remote's `push` refspecs for a bare push), less what is on a tracking ref (`refs/remotes/<name>/*`, but those a prototype branch's code can be stored under, #393, below) of a remote whose fetch URL (read as git fetches, `insteadOf` applied) is `project.repo`. The commits a merge brings in that aren't on such a tracking ref are sent too, and judged as any commit; so are a cherry-pick's new commits. A word is a remote's name when the repository defines that remote (git looks it up first, so a remote's name may hold a `/` or even a `:`); otherwise it is a URL, and from a directory the guard can't follow, a word with a `:` or starting a path (`/`, `.`) is one. A push given a URL is judged by that URL, stripped the same way, and a bare push goes where git sends it (`branch.<name>.pushRemote`, `remote.pushDefault`, `branch.<name>.remote`, else `origin`). With no `project.repo` in the profile, every push is judged. A push by URL to another repository, from any directory, and a `--dry-run`, are as today; so is one by a remote's name whose URL is another repository's, from a directory the guard can follow.
- **A revert** (#392) that exactly undoes a commit already on the base goes through the commit and push rules. A commit made by `git revert` names the commit it reverts ("This reverts commit <sha>", full or abbreviated, as `--reference` writes it; a branch or tag of that name doesn't stand in for it). When that commit is on the base branch's remote ref (`<remote>/<base>` of a remote fetching from `project.repo`, or `origin`'s without one, as last fetched) and the revert's code paths are as git's own revert of it leaves them, it is a revert, not code. git's own revert is that commit's change (for a merge, against its first parent, as `git revert -m 1` makes it) undone on the revert's parent, merged as `git revert` merges (`git merge-tree`), with git's own text merge only, with no conflict in a code path. The guard merges in an empty repository of its own that borrows the project's objects, so no config, attribute, merge driver or `merge.default` of the project's, the session's or the system's decides a line (`merge=union`, which keeps both sides' lines rather than marking a conflict, makes a conflict there), no program or hook runs, and nothing is written to the project. Only the revert is let through: other commits a push sends are judged as before. Any other revert (one resolved after a later change to the same or the next lines, one with more changes, of a commit that isn't on the base, or naming none here) is refused: the refusal offers GitHub's own **Revert** button on the pull request the reverted commit merged, once it is on the base (its subject `Merge pull request #<n> from …`, or a squash merge's `… (#<n>)` on the base's first-parent line) and unless git's revert conflicts (GitHub's would too), and otherwise a quick ticket for a ticket session, worded as the skills offer a run; one of a commit not on the base, or not here, says to run `git fetch` first, since it may have merged since. **In the conductor,** a matching revert is allowed only for a commit its run's ledger records the owner as allowing, an entry `{"what": "revert", "revert": "<the full sha>", "at": …, "grant": …}` in the state block of the run's local body file (`.workflow/run/body.md`; the full SHA in lower case, as `WF state put` writes it, so a SHA-256 repository's conductor is allowed none, and its refusal says the owner makes the revert); entries without a `revert` field, or with another `what`, don't count, and a body file it can't read allows none. Without one, it is refused, saying to ask the owner and, once allowed, to record that entry; a revert that doesn't match is refused even when allowed, saying to tell the owner (and to record it as not made, when it has an entry). When the guard can't read whether a commit is an exact revert (a git read failing or taking too long, no remote ref of the base here, a shallow clone without the commit's parent, more than 64 reverts or 8 seconds of reading them in one command), the commit or push is one it can't tell about (below), and a code commit beyond it in the same push is still refused. A revert made with other merge settings than git's own (a merge driver, a `merge` attribute, `merge.renames`, `merge.renormalize`) may read as not exact. It needs git 2.40 or later (`git merge-tree --merge-base`): with an older git, a revert that carries code is asked (refused in the conductor).

a directory it can't follow or that doesn't exist yet, or one another part of the command makes a repository or worktree in (`git init`, `git clone`, `gh repo clone`, `git worktree add`); `GIT_DIR`, `GIT_CONFIG_GLOBAL`, `HOME` and the like set for the push or anywhere in the command (exported, declared; `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_KEY_<n>` by the keys they set, below, unless one is added to with `+=` or exported bare, or `GIT_CONFIG_COUNT` or a `GIT_CONFIG_VALUE_<n>` is set without each of its keys, which then come from outside the command); another part of the command that may move a branch, a tag or HEAD (`switch`, `checkout`, `reset`, `commit`, `merge`, `update-ref`, a writing `branch` or `tag`, a `fetch` naming a destination (a refspec or `--refmap` with a `:`), a push into this repository (`.`, its path, a remote whose URL is one of those), git run by its dashed name, `gh pr checkout`, `gh repo sync`, any git command it doesn't know to change none), more pushes than it can read in 15 seconds, since the guard reads the repository as it is when the command starts, and for a push with no remote named, wherever it seems to go (git picks its remote by the branch checked out when it runs); or, for a push to `project.repo`'s URL, when nothing else is, the command naming a `.git`. **A push by a remote's name, or with none named,** goes where the config of the repository git reads says, so it is can't-tell when the command can change that config or which repository git reads, wherever the push seems to go: `GIT_DIR`, `GIT_CONFIG_GLOBAL`, `HOME` and the like set for it or anywhere in the command, `-c`, `--config-env`, `GIT_CONFIG_PARAMETERS` or `GIT_CONFIG_KEY_<n>` setting a `remote.`, `url.` or include key, `push.default`, or a branch's `remote` or `pushRemote`, another part of the command that writes one (`git config`, by its key, both names of a renamed section, an option it can't read or an edit counting as any; a key alone is a read; `git remote add`, `set-url` and the rest; a shell write the guard places on the global git config; for a push with no remote named, a push with `-u`), or a repository another part of the command makes there; and, when it seems to go elsewhere, a `.git` the command names. **A push given a URL** of another repository is as today, unless something in the command may send it elsewhere: `-c` or `--config-env`, a `GIT_CONFIG_PARAMETERS` or `GIT_CONFIG_KEY_<n>`, or another part's `git config` write, setting a `url.`, `remote.` (a remote of that name, which git looks up first; `git remote add` refuses a name with a `:`) or include key, or a key the shell spells (a variable, a substitution, a brace list, a glob in its section or name, where git allows none; a subsection's `*`, as in `http.<url>.*`, is git's own); a shell write to the global git config; a config variable added to with `+=` or exported bare, or a `GIT_CONFIG_COUNT` or `GIT_CONFIG_VALUE_<n>` set without each of its keys (which come from outside the command); or, from a directory the guard can follow, a `.git` the command names. Then it is can't-tell too. A push given `project.repo`'s URL (one that isn't also a remote's name) together with what it sends (a refspec, `--all`, `--mirror`, `--tags`) is judged whatever the remote and push settings say, unless the command sets a variable that changes which repository git reads (`GIT_DIR` and the like); without them, `push.default` says what it sends, so it is held to the remote-name rule above. Settings that may rewrite a URL make any push can't-tell, as above. `GIT_CONFIG_PARAMETERS` is read as git reads it (its `'key'='value'` and older `'key=value'` items, git's own quoting), after the shell: a value the shell spells (a variable, a substitution, a brace list, a tilde), or one it can't read as git would, counts whatever its keys. A push by a remote's name from a directory it can't follow is asked too, even to another repository: the release gate's `git -C "$SANDBOX" push -u origin …` is, until it pushes by URL or from a directory the guard can follow.
- **The refusal** names the path and says what to do instead, as the skills offer it: hand it to a conductor run (**Run it unattended**); **Set up unattended runs** first while no ticket environment is named; in plugin mode, a session on the owner's computer started with `WORKFLOW_ROLE=ticket`; or change `guard.code_writers` in a pull request for the owner to merge. The conductor's names its own way: with the charter's `conductor_fixes` on, a `workflow:infra` ticket for a ticket session, else `for_owner` (read from the run's local body file, `.workflow/run/body.md`; both are named when it can't be read).
- **What stays as today:** docs, protected paths, `.workflow/`, settings files, running and reading commands (tests, scripts, `workflow`), GitHub's direct file changes (the contents API, the GitHub MCP file tools), every decision under `"any"` or with `code_writers` absent, and ticket sessions' rules.
- **It is a seatbelt, not a wall.** It doesn't see a target it can't place (a path relative to a directory it can't follow, a patch it can't read, a script or interpreter that writes files when run, `python3 -c …`), code written in a clone that isn't one of Claude Code's worktrees, PowerShell paths after a `cd`, a PowerShell word that names nothing there yet and holds no `/`, `.` or glob (a new `Makefile`), a patch's `-p` or `--directory` (each file is placed as git places it by default, judged file by file), or a session that edits the vendored guard, turns hooks off or sets `WORKFLOW_ROLE` in a settings file's `env`. A commit catches code written in those ways in the project's repository (above) once it is written: it judges the index and the working tree as they are when the command starts, so not what runs earlier in the same command (a `git add`, #394, a script or interpreter that writes files, `git cherry-pick -n`, `git merge --squash`, `git checkout <tree> -- <path>`, `git stash pop`; a `git restore --staged` is refused as if still staged), a variable exported earlier in the command, a pathspec file written through a symlink or by a later turn of a loop, a `cd` that fails or an earlier `git init`, `git clone` or `git worktree add` that fails (when the commit runs after it anyway, chained with `;`), a directory that is there already but that the command removes, moves or repoints (a link) before the commit, a `.git` it writes without naming it in a repository already there (one a variable, a glob, a brace list or another command spells out), the code an `--amend` keeps from the commit it replaces, commits made with plumbing (`git commit-tree`) or inside `git rebase --exec`, git aliases, or a commit's own hooks; an unknown command word before `git commit` is read as running it, while git's dashed `git-commit` counts only as the command word; a push that carries code is the next check (#390). The push rule judges commits, not how they were made, so it doesn't see a remote-tracking ref of `project.repo`'s remote made or moved locally in an earlier command (`git update-ref refs/remotes/origin/…`, a push to another repository while that remote's push URL pointed there, another remote's fetch refspec writing into its namespace, a tracking ref left by a `fetch` refspec since changed, or one filled from a `prototype/*` branch by `git fetch` given its own destination), a script or program that switches branches, an alias or function loaded from the user's own shell (`gco`), or a write to a `.git` a glob or variable spells, before a prototype's write or commit in the same command (#393; such a commit stays local, and a push of it is judged), a branch made or moved on GitHub's side from a `prototype/*` branch (GitHub's **branch** button or `create_branch`, the refs, merges or rename API), which then counts as on the remote once fetched (#393), a URL given on the command line that `insteadOf` or `pushInsteadOf` (set on disk, or in config a variable points to) rewrites into `project.repo`'s (a remote's URL is read with them), a repository a command other than git makes or fills in the same command (`cp -r`), a variable the shell sets other than by a `NAME=value` the guard reads (`read`, `printf -v`, `for NAME in`, a name the shell builds, as `export GIT_CONFIG_$A=…`), a glob the shell matches against a file the command made for it, a push run through a git alias or by a script or interpreter, or GitHub's own file changes; and with a remote fetching from another repository, its tracking refs don't count as on `project.repo`. The revert rule trusts the commit `git revert` names: a commit whose code paths are as git's own revert of a commit on the base leaves them passes as a revert, whoever made it, a revert of a revert (which puts the reverted change back) included; beside a commit finishing a revert, it doesn't see a program git runs during a read (an fsmonitor or external diff set in git's config, a hook), which the push then judges by what the commit carries; and the conductor's revert allowance trusts the ledger in its local `.workflow/run/body.md`, a file the conductor writes, without checking that the owner's words or the run are real. A working tree's profile that is missing or invalid isn't replaced by the base's here yet: an invalid one takes the can't-decide fallbacks below, and with a missing one an attended session's tools go through, as before.

**When something is wrong it fails closed** in ticket and conductor sessions (`WORKFLOW_ROLE` set, or set to a value it doesn't recognise, which counts as ticket):
- an invalid or missing profile (an invalid profile, a malformed event or a failure outside the guard on a branch matching the profile's `run.ticket_branch` line counts as a ticket session even with `WORKFLOW_ROLE` unset, the branch read as the old-Python fallback reads it);
- a malformed hook event;
- an error in the guard itself;
- the guard running out of time: 25 seconds after the kit's CLI starts loading, under the hook's 30-second timeout, its check is refused with its own reason (since 0.1.10, 12 seconds under 15 until #57; where Python has `SIGALRM`, which Windows lacks). Reading the session's role counts too: one not read in time counts as ticket;
- the kit's CLI missing from the checkout. Then everything is refused except `git checkout -- .claude/workflow` or `git restore .claude/workflow`, which restore it;
- `python3` older than 3.11, missing, or failing to run the kit (since 0.1.8). Every tool is refused until the session runs on Python 3.11 or later. Here the CLI can't run to read the role, so the fallback reads it more simply: `WORKFLOW_ROLE`, or with it unset and the kit set up, a branch matching the profile's `run.ticket_branch` line (its first plain `ticket_branch = "…"` line; written another way, the default `claude/build-*` is used). With no working `python3` it can't read the hook's event either, so it reads the project directory's branch, not a worktree's. `workflow doctor` still runs on an old `python3` (since #61) and gives a short report instead of a bare error: `python3`'s version as a gap with its fix, and every other line the full doctor gives (the kit, GitHub, Cloud), with the same ids and groups, as can't check until `python3` is 3.11 or newer. `--json` gives them in the full doctor's shape, it exits 0, and `--strict` exits 1. Its wording follows `WORKFLOW_EXPERIENCE` or `.workflow/experience`; the profile's default can't be read there.

**When the guard's hook itself fails, the tool is blocked,** in every role, attended sessions included (#57): the guard's entry carries `"onFailure": "block"`, so a hook that runs past its 30-second timeout, can't start (its command or `sh` missing), exits non-zero or prints output Claude Code can't read blocks the tool instead of letting it run. Claude Code discards a timed-out hook's output, so a timeout blocks even where the kit itself would have allowed the command. The kit's hook commands catch their own failures and exit 0, so only these block. When a timeout blocks a command, Claude says so and offers to split or simplify it (a line in the kit's CLAUDE.md section). The Stop gate, the prompt hook and the session-start hook keep the default (`continue`): blocking a Stop on failure would loop, and blocking a prompt would lose it.

**The oldest Claude Code these protections need is v2.1.295,** for the timeout and can't-start protection above. An older version ignores the `onFailure` field and keeps the hooks (checked on 2.1.294 in #54), so everything else here still holds there, but a guard hook that times out or can't start lets the tool run.

**In attended sessions the guard takes the can't-decide fallback** (since #53) when the guard raises or runs out of time, the profile is invalid, the hook's event can't be read, or `python3` is older than 3.11, missing or failing (since #56: the hook command reads the event's raw text with `sh` and `awk`, in `scripts/workflow/fallback.sh`, in a vendored project and in the plugin alike):
- a push or a merge (`git … push`, `gh … pr … merge`, the GitHub MCP tools that push, write files or merge: one definition, in `scripts/workflow/fallback.py`) is asked;
- it is refused in solo mode (the profile's first plain `ruleset = false` line, read without the kit, so an invalid profile still counts) and in a permission mode where nobody is asked (`bypassPermissions`, `dontAsk`, or one the kit doesn't know; an absent mode counts as one that asks). There the refusal also says how to be asked (switch the permission mode) and that you can do it yourself, without repeating the command, since nothing could check it for sensitive data;
- everything else is left alone: no decision.

The reason says the guard isn't working, why if known (the error, the profile's error, the Python version), and how to fix it: run `workflow profile check`, check that `python3 --version` is 3.11 or newer, and report the error (on an old `python3`, install a newer one; after a timeout, split the command). A truncated event is read to its end for its tool, command and mode. The guard's hook always exits 0 in an attended session, printing the fallback's decision or nothing. Unchanged: ticket and conductor sessions keep refusing every tool as above; a missing profile in an attended session (the kit isn't set up) is left alone, except on an old `python3`, where pushes and merges are still asked (refused where nobody is asked), as since 0.1.8, since the plugin's hooks run there without a profile; the Stop gate, the prompt hook and the session start keep reporting their own errors, and with `python3` missing or failing the session start also says what is wrong. The plugin's hooks run the same commands from the plugin's directory; the plugin is for attended work, so without a working `python3` it never refuses every tool.

**It can't see** a script file the session writes and then runs (a vim script sourced with `-S` included), text piped into a shell, network calls made by programs (an interpreter's `subprocess.run(['git', …])`, `wget`, `fetch`), or deliberately obfuscated commands. It is a seatbelt for honest mistakes, not a wall against an adversary. That is why the ruleset and the credential-free environment come first.

**A lesson from building this kit:** a review agent testing the guard ran its own test cases by accident. Its heredoc's delimiter appeared inside a case, so the shell ran the rest as commands. One of them pushed to the kit repo's `main`, which had no active ruleset at the time. Reviewers and explorers that try dangerous commands work only in throwaway copies, never in the real checkout, and the ruleset is what makes such an accident harmless.

## 5. Checking the set-up

Ask Claude to **check the set-up** (the `check-setup` skill), or run `workflow doctor` yourself: one report of what's set up and what isn't, each line with its fix, the most serious first. Neither changes anything. In a cloud session, `check-setup` gathers what only a session can see (the rulesets and repository settings through the GitHub tools, the base branch's latest check runs and statuses and the open pull requests, the environments with `list_environments`, the `workflow:run` issues and Claude Code's version), hands them to `workflow doctor --json` as files, shows the report in words that suit you, and offers each upgrade it names ("Protect `main`", "Restore protection", "Set up unattended runs", "Require these checks", "Use a merge queue") as a choice with "Not now", protecting first. In a local session it runs doctor with what `gh` gives, and says the environments can only be checked from a cloud session. The guided start offers it when its quick local look (`workflow status`) finds a gap, and once a session in solo mode.

The checklist below is what doctor checks, kept as the reference: what an owner, or a cloud session asked to "check the workflow set-up", looks at by hand after the set-up pull request merges. Only a cloud session can list the account's environments. Report each item as fine or as a gap with its fix; change nothing.

1. **The ruleset:** `gh api repos/<repo>/rulesets`, then `gh api repos/<repo>/rulesets/<id>` for each:
   - `enforcement` is `active`, and `conditions.ref_name.include` covers the base branch (`~DEFAULT_BRANCH` or `refs/heads/<base>`);
   - `bypass_actors` is empty;
   - its rules include `deletion` and `non_fast_forward`;
   - `pull_request`: `required_approving_review_count` 0 (more is a choice, with the consequence in §1) and `require_code_owner_review` false;
   - `required_status_checks`: every name in the profile's `ci.required_checks` (vendored mode includes `workflow kit`), and `strict_required_status_checks_policy` true, or false beside a `merge_queue` rule, which meets it;
   - no `required_linear_history` rule.
2. **The merge settings:** `gh api repos/<repo>`: `allow_auto_merge` and `allow_merge_commit` are true.
3. **CODEOWNERS** (§3) covers `/.claude/` and `/.github/workflows/`.
4. **The environments** (§2): `list_environments` shows both names in the profile's `run.ticket_environment` and `run.conductor_environment`. Nothing can read what an environment holds, so ask the owner to confirm the ticket environment has no secrets and `WORKFLOW_ROLE=ticket`, and the conductor's `WORKFLOW_ROLE=conductor`.
5. **The kit:** `python3 -B .claude/workflow/bin/workflow.py profile check` (no errors; read the warnings) and `vendor verify --strict`.

`workflow doctor` reports all five items in one go, each line with its fix: with `gh` signed in it reads the rulesets and settings itself (only reads), or takes them as files (`--rulesets`, `--repo`, as `workflow protection` takes them); without either, the GitHub lines are "can't check" and say how to check them. CODEOWNERS is read from the checkout. With the base branch protected and outside solo mode, it reads the checks that ran on the base branch's latest commit (`--checks`, their check runs and statuses in one file, or `gh`) and, when some aren't required yet, offers "Require these checks" (`require_checks`) on the required checks' line, naming each; the try-it link's check is never counted. A check the ruleset requires that the profile doesn't list is a note naming the open pull request that carries `<!-- workflow:required-checks -->` (`--prs`, the open pull requests, or `gh`), a gap with none open, and "can't check" when the pull requests can't be read; in solo mode it is a note, to put right once solo mode is left. The environments (item 4) come only as a file, `--environments`, with `list_environments`' JSON, since only a cloud session can list them; without it their line is "can't check". Both found, and active, is fine. One missing is a gap naming it. Neither is a note offering "Set up unattended runs" while no run has been made, and a gap once one has. A run is an issue labelled `workflow:run`. Doctor reads them with `gh`, or from `--runs`, which takes the issues as `charter estimate --runs` does. A name that differs at all, even by a letter or its case, isn't found, and a close one is named as a likely typo. One environment named for both roles is a gap. The note that nothing can read what an environment holds is always there.

The Previews group (try-it links, [Add try-it links to your pull requests](previews.md)) is read from the checkout. With the profile's `[previews] on = true`, the Wrangler config, `wrangler.toml` at the project's root read as TOML, must have a `[previews]` block: without one it's a gap, whose fix links that page and names the "missing a `previews` block" failure Cloudflare shows. A `wrangler.json` or `wrangler.jsonc` is "can't check", with a fix naming the `"previews"` key to look for, and so is a `wrangler.toml` that isn't valid TOML or isn't a readable file. With `[sensitive]` patterns, `access` must be true as well: otherwise it's a gap, saying in plain words what `profile check` refuses; when true, the line says the kit relies on the owner's word for it. A Wrangler config with no `[previews]` section is a note offering "Add try-it links" (`add_try_it_links`), so `--strict` passes; a section that doesn't turn them on is a note with no offer; with neither a Wrangler config nor a section, there's no Previews line. `check-setup` offers it, and `upgrade-setup`'s "Add try-it links" makes it: the steps in Cloudflare one screen at a time, then a pull request setting `[previews] on = true`, merged by the owner.

In every run's pre-flight the conductor runs `workflow doctor --json`, with the rulesets, the repository's settings, the environments, the `workflow:run` issues, the base branch's latest check runs and statuses (`--checks`) and the open pull requests (`--prs`) as files and its Claude Code version as `--claude-version`, and shows each gap or line it can't check as a safety gap, with its fix, to fix first or to accept for that run. "Require these checks" is asked "Require these checks first" (done in an attended session, the kick-off ending there: the conductor never changes the ruleset itself) or "Go ahead without them". Solo mode and removed protection are read from doctor's lines. A missing ticket environment stops the run whatever doctor says.
