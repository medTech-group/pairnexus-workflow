## Helpers

- `_read`: in `cli.py`, the text of a file a command was given, or standard input's for `-`. A file that can't be read raises `InputUnreadable` (an `OSError`, with the errno, reason and file name it had; an empty path, refused before reading, or standard input closed has no errno, and reads "no path was given" or "standard input (-) is closed"), one that isn't UTF-8 text, standard input's too, `InputNotText` (a `UnicodeDecodeError`), so a command that catches either words it itself; `main` refuses any other in one line, `` workflow: can't read `<path>`: <why> ``, never a traceback (#687). `_json` reads through it.
- `_issues_file`: in `cli.py`, a `--issues` or `--prs` file as the GitHub API lists it: a list of objects with a number (`doctor._number`), or `--paginate --slurp`'s pages of them, flattened with `_fetch_items`. Its text is read as JSON with `doctor._parse_json`. A file that isn't JSON, or isn't such a list, raises `InputUnreadable` with no errno, so `main` refuses it in one line (`_parse_json`'s reason, such as `` it isn't valid JSON (…) `` or `it is empty`, or `_not_a_list`'s, `` it isn't a list of issues (it is …) ``). `workflow status` (#757) and `workflow ready` (#779) read both their files with it.
- `_stdin_taken`: in `cli.py`, the one place for the words refusing a second `-`, from the flag refused and the one that already read standard input: `` --<flag>: standard input (-) is already --<owner>'s: only one file can be read from it ``, or without the `--<flag>: ` when no flag is given. `_stdin_taken_line`, `_json_inputs` (merge-check, preview and the other commands reading through it) and `ready`'s `--permissions` give them through it (#794); a refusal of the same case uses it rather than its own words.
- `_stdin_taken_line`: in `cli.py`, the one `workflow <cmd>:` line refusing `--issues -` with `--prs -`, or None: standard input can be read once, so `--prs` would find it empty after `--issues` read it. It says `` --prs: standard input (-) is already --issues's: only one file can be read from it ``, through `_stdin_taken`, and is checked before either file is read; `workflow status` and `workflow ready` print it and exit 1 (#794). `status` and `ready` refuse `--issues -` with `--prs -` before reading either; `_json_inputs` gives the second `-` its reason without reading it, after reading the first; and `ready`'s `--permissions -` gets its note when `--issues` or `--prs` read it.
- `_not_a_list`: in `cli.py`, why a JSON value isn't a list of issues or pull requests, or None. It holds the one test of the list: a list with nothing in it, however its lists nest, but objects is one, read through `_fetch_items`; the caller gives only how deep it reads (`deepest`) and what each object needs (`each`: a file's whole-number number, `doctor._number`). Any other list is "a list holding something other than issues", and anything else is named by its kind (`it is a number`), GitHub's error object with its message through `reviews._shown`. `_issues_file` gives a file its reason, 2 lists deep, each issue numbered (#757), and `_fetch` what `gh` gives (#789); a refusal of the same shape uses it rather than its own test or wording.
- `_print_text`: in `cli.py`, prints a command's text with each character standard output's encoding can't take written as Python's backslash escape (`\U0001f600`), the rest as it is, so a cp1252 or ASCII output never ends the command in a traceback; a stream that names no encoding takes the text as it is. `workflow status`'s and `workflow protection`'s text print through it (#786), and `workflow ready`'s (#802); a command's text with the same traceback calls it rather than printing directly.
- `_unnumbered`: in `cli.py`, why `_fetch`'s issues or pull requests can't be read, or None: each needs a whole-number `number` (`doctor._number`), as `_issues_file` asks of a file's. `workflow status --fetch` refuses them in one line with it, `` workflow: can't read the issues `gh api repos/<repo>/issues` gave: N of M has no whole-number number (…) ``, the repo shown through `reviews._shown`, exit 1, never a traceback (#775). Its wording of what was read is `_gave`'s.
- `_unnumbered_line`: in `cli.py`, that one `workflow:` line for `_fetch`'s issues and pull requests (the issues named first), or None, through `_unnumbered`: `workflow status --fetch` (#775) and `workflow ready --fetch` (#790) print it and exit 1. A command that needs every item's number from `_fetch` (one that would otherwise fail on an item without a whole-number one) refuses through it rather than another check. `workflow state join --fetch` needs no refusal: it reads past such an item, as it reads past any issue that can't be a ticket of the run (`state._candidates`).
- `_fetch`: in `cli.py`, the issues or open pull requests through `gh api`, its pages flattened. It reads `gh`'s output as JSON with `doctor._parse_json`, the reader `_issues_file` uses (an old `gh`'s pages one after another with `posts.decode_values`), and flattens it with `_fetch_items` at most `FETCH_DEPTH` lists deep, counting the list `_fetch` holds it in (`gh`'s output up to 7 deep); output that isn't JSON, holds a number too long or nests lists too deeply raises `FetchUnreadable`, a `SystemExit` whose code is one line, `` workflow: can't read <_gave's words>: <why> (fetch them …) ``, exit 1, on the `--slurp` route and an old `gh`'s. On the page-by-page route (`fetch.by_page`, #568), only lists nested too deeply that Python's own reader can read raise it; that route's other refusals are #810's. On every route, output that isn't a list of objects, or pages of them, raises it too, with `_not_a_list`'s reason, the one an `--issues` file gets (#789): `--slurp`'s checked whole, as a file is, and each page an old `gh` prints or read one at a time on its own. Its `gave` and `why` are there for a caller with its own wording (`state join`) (#788). When `gh api` fails, its `gh api repos/<repo>/… failed: …` line shows the repo through `reviews._shown`, as `_gave` does, `fetch.by_page`'s own message included, so it stays one line (#792). `status`, `ready` and `state join` fetch through it.
- `_gave`: in `cli.py`, what `_fetch` read, as a refusal names it: `` the issues `gh api repos/<repo>/issues` gave `` (or the pull requests'), the repo shown through `reviews._shown` (#788). `FetchUnreadable` and the `_unnumbered` refusal (`_unnumbered_line`) both use it.
- `_fetch_items`: in `cli.py`, the objects in pages of lists, in order, read without recursion, so no nesting ends in a `RecursionError`; with `deepest`, lists nested deeper raise `TooDeep` (#788); with `only_objects`, anything in them but a list or an object raises `NotAnObject`, where it is otherwise left out (#789). `_fetch`, `_issues_file` and `graph cites` flatten with it.
- `as_read`: in `status.py`, an issue or pull request as `workflow status` reads it: a copy with each field it reads that holds the wrong type left out (`state`, `state_reason`, `title`, `body`, `head` and its `ref`, `draft`; a sub-issue or dependency summary whose count isn't a whole number, left out whole), so the item reads as it would without that field, never a traceback; a `pull_request` of the wrong type, or null, still marks a pull request, read without its details. It leaves labels as they are: `issues.labels_of` reads past one of the wrong type (#772). `snapshot` reads every issue and pull request through it, from `--issues` and `--prs` files and `--fetch` alike (#770), and so does `workflow ready` before `issues.readiness` (#780), rather than a check of its own, with `by_count`: a summary loses only its count of the wrong type, so a parent whose `total` is a whole number stays a parent (`issues.is_build_ticket` reads `total` alone). `snapshot` reads readiness, and whether an issue is a parent, through it with `by_count` too, so a parent is never a ready ticket in either, as `ready` reads it; its sections' counts keep the summary left out whole (#799).
- `_paths`: in `evidence.py`, names paths in a message: the first five, then "and N more"; in a report, each a code span on one line (`_code`: in ASCII, quoted as git quotes it, `_git_quoted`, when it holds a control character, a byte outside ASCII, a double quote or a backslash, and fenced past its backticks).
- `_dirty_store`: in `evidence.py`, the emptied `<sha>-dirty` store, where a run keeps what didn't run on the commit itself (a dirty tree with `--allow-dirty`, or a tree that changed mid-run), apart from the commit's evidence and never reused.
- `tree_state`: in `evidence.py`, a look at the whole checkout's tree, from its top even when the project is a folder in it, outside the project's `.workflow/`: each tracked or staged path's index entries and `lstat`, and the untracked files that aren't ignored (a checked-out submodule's HEAD and its own tracked and untracked paths in its place), and the `lstat` of each folder that isn't ignored (one holding a tracked path, or none: an empty one, one holding only ignored files, and those beneath). `tree_changes` gives the paths that differ between two looks; read-only git commands change neither.
- `proc.run`: runs one of the kit's own short commands with no shell and no input, in a session of its own, and kills its whole process group whenever the caller stops waiting (a timeout, a Ctrl-C), holding a Ctrl-C that comes while it starts; a Ctrl-C still reaches the caller as `KeyboardInterrupt`. Doctor's `_run`, `workflow status`'s `git` call, the profile's `_git` and the evidence run's tree look (`_git_out` in `evidence.py`) use it.
- `proc.output`: what a command printed, as UTF-8 with other bytes replaced, when it exited 0; else None.
- `ascii_link`: in `research.py`, the link in ASCII: the host encoded by UTS 46 non-transitional rules, the userinfo, path, query and fragment percent-encoded as UTF-8. `fetch` sends a link outside ASCII without its userinfo, as a browser does; a link in ASCII as written. `fetch` and `link_problem` both use it, so a link that can be saved is one that can be fetched.
- `is_fingerprint_start`: in `research.py`, whether a file is a fingerprint file from its name and the start of its text (named `*.fingerprints`, or its first line a `url:` line); `research check` reads a topic's folder with it, and `workflow graph` leaves such files out.
- `sentences`: in `graph.py`, a text's sentences as spec #682's "What it gives back" ends them (an end mark with any closing quote, bracket, emphasis or backtick before a space or the line's end, except after "ans", "e.g" and "i.e"; a blank line; the end of a heading, a list item or a table row), with each line's pieces mapped to them, so a citation finds its sentence. Answer ids (#745) find theirs with it.
- `labels_of`: in `issues.py`, an issue's or pull request's labels, casefolded, as GitHub matches them: names, or objects with a text `name`; a label of any other type is read past, the others kept, and a `labels` field that isn't a list reads as none. `workflow status` reads labels only through it, `as_read` keeping no filter of its own; `ready`, `state` and `workflow graph` read them through it too (#772), and so do `workflow doctor` (`doctor._label_names` is it) and the conductor's estimate (`estimate.past_runs`), each keeping no reading of its own; an empty name, `""` or `{"name": ""}`, is read past in every reader (#778).
- `is_whole`: in `issues.py`, whether a value read from JSON or TOML is a whole number: an `int`, never a `bool`; a float such as `3.0`, a text such as `"3"` and None aren't. Every whole-number check in the kit calls it, adding its own range: `status._whole` (or missing), `state._int`, `doctor._number`, merge-check's numbers, the profile's and the charter's limits, and the readers of comment ids, findings' issue numbers and diff counts (#773).
- `escape_surrogates`: in `issues.py`, text with each lone surrogate (half a surrogate pair, which UTF-8 can't encode, so printing it ends in a traceback) written as JSON escapes it, `\ud800`; everything else is left as it is. `status.text` passes `workflow status`'s text through it, `protection.printable` calls it (#774), and `workflow ready`'s text passes each ticket's line and each `note:` line through it (#785).
- `has_control`: in `issues.py`, whether text holds a control character, Unicode's Cc set exactly (C0, DEL and C1: U+0000 to U+001F, U+007F to U+009F), through `issues.CC`; a separator, a bidirectional override and a backtick aren't in it. The kit's one test of that set: `profile.parse` refuses a `project.repo` holding one through it (#821), and `escape_controls` builds its own set from the same one (#823); a check whose set is exactly Cc calls it rather than keeping its own. `research`'s page check (Cc less tab, line feed, form feed and carriage return) and `protection.NOT_IN_A_CHECK` (Cc, surrogates and separators) keep their own, since neither is exactly Cc. A test that needs a control character past the profile patches `issues.CC`.
- `escape_controls`: in `issues.py`, untrusted text (an issue's or pull request's title, a detail, a branch) as a terminal may show it: each control character (C0, DEL and C1, escape codes' `\x1b` among them), the line and paragraph separators (U+2028, U+2029) and the bidirectional embeddings, overrides and isolates (U+202A to U+202E, U+2066 to U+2069) written as JSON escapes it (`\n`, `\r`, `\t`, else `\u001b`), so a title can't add a line of its own or reach the terminal as a code; everything else, text outside ASCII, an emoji's joiner, a right-to-left mark and a lone surrogate (`escape_surrogates`'s) among it, is left as it is. `status.text` passes each item's title and detail through it (#776), and `workflow ready`'s text each ticket's title, area, reasons and `note:` lines (#797); a command's text that prints an issue's or pull request's text calls it rather than keeping its own list.
- `is_spec`: in `issues.py`, whether an issue is a spec: the `spec` label, or a "Spec:" title. `is_build_ticket`, `workflow status` and `workflow graph`'s `kind` use it.
- `replaces_lines`: in `graph.py`, the lines of a body's own `## Replaces` section, from its heading to the next, never from a fenced block or a `>` quote. `built_by` (#746) reads its ids from these lines.
- `holds_sensitive`: in `profile.py`, whether a text matches any of the profile's `[sensitive].patterns`. The guard (`_text_holds_sensitive`, which `_bash_holds_sensitive` calls) and `workflow graph`'s `_shown` use it, rather than each keeping its own `re.search` loop over the patterns (#756).
- `sensitive_match`: in `profile.py`, the first of the patterns found in a text, else None; the guard's two refusals that name the pattern use it, and `holds_sensitive` reads it (#756).
- `unnameable`: in `research.py`, why no key-source line could name a link (a space, a line break, a control character, `<` or `>`), else None. `ascii_link` and `link_problem` both refuse such a link with it.

## Rules

- `evidence.py`: a run keeps a shard's result as the commit's only after checking, once the shard has ended, the working tree and then that HEAD hasn't moved. A moved head stops the run with nothing kept for that shard, so a later run on the commit runs it again (#671). A tracked or staged path changed since the last look (`tree_state`, inside submodules too, the repair's window included), or with `--allow-dirty` an untracked file that appeared or a file created or removed in a folder that isn't ignored (an ignored file too, even one gone again), makes the run a dirty one: it goes on, keeps that shard and every later one under `<sha>-dirty`, and its report carries the dirty marker. Untracked files that appear without `--allow-dirty` are left be (#704). The base branch's worktree, fresh from git, isn't checked at all (#703).

- `profile.py`: every `git` call goes through `_git`, so through `proc.run`, and its timeout is a module-level seam (`GIT_TIMEOUT`, or `CODE_FILES_TIMEOUT` for the tracked files), never a literal at the call, so the Ctrl-C tests can raise it past their wait (#690).

- `graph.py`: the project graph reads the base branch only at `origin/<base>`, fetched first (`small.base_ref`), never the working tree, and writes nothing else; it reads the files that may cite an id through `git grep` at that ref (binary files left out by git), so only the files that may cite an id are read whole. It spends no model tokens. A run whose state can't be read never stops it: its line goes under the list, or to standard error with `--json`.

## Decisions

- Doctor's process-group kill (#684) moved into `proc.py` rather than being copied, so `workflow status` and the profile's `git` reads share it (#689).
- A host outside ASCII is encoded only where the standard library can be sure it encodes it as a browser does, and refused as can't fetch otherwise: the kit has no UTS 46 mapping table, and Python's own `idna` codec is IDNA 2003, which turns `faß.de` into `fass.de` (#532, [#560](https://github.com/medTech-group/pairnexus-workflow/pull/560)).
- `workflow graph cites` is its own module, `graph.py`, so the vendored copy's lock records when a project got it (spec #682, "The command's form"); its `--json` objects carry `built_by` and `changed_by` empty until #746 and #745 fill them, so the form is the spec's from the first ticket (#744).
