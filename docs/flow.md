# The flow: plan → spec → build tickets → code

Every session that plans, writes a spec or builds a ticket follows this file. Each kind of session ends by reporting its checklist, every line marked done or saying why not, so a skipped step shows.

The project's specifics live in its profile: `.claude/workflow/profile.toml` (commands, required checks, protected paths, areas, release steps, and `project.rules`, the list of the project's rule documents) and `profile.md` (sensitive data, secrets, environment notes). Read both before acting. Where this file says "the project's rules", it means the documents in `project.rules`.

**Skills.** Skills named here are in `.claude/skills/<name>/` (vendored) or under the plugins (`pairnexus-workflow:<name>`, `mattpocock-skills:<name>`). A skill marked user-only can't be loaded with the Skill tool: read its `SKILL.md` and follow it as written.

**Starting.** In an attended session, the `start` skill begins at the first message (or `/start`): it asks what we're working on, with choices, splits a request into items, proposes a path for each, and files them as issues. At each later message of an attended session, the kit's hook adds a one-line reminder: new work that isn't part of the plan or ticket already agreed is split into items and the plan agreed first. Or name the work ("implement #146", "work the doctor map"), or use `next`: it finds what is ready and does one piece under this file.

**Handovers.** In an attended session, end each step by offering what comes next as choices (the `AskUserQuestion` tool), your recommendation first: after an interview, a spec, a breakdown, a charted map, a light item and finding a bug's cause. The `start` skill lists them for each step. After a map decision or a build, recommend going on in a fresh session.

## 1. Planning (optional): a map, one decision per session

A large effort can start as a **map**: an issue labelled `wayfinder:map` whose child tickets are the decisions to make with the owner (grilling, research, prototypes, tasks). Follow the `wayfinder` skill. Small efforts skip this and start at a spec.

1. **Claim** the ticket (the `workflow:in-progress` label and an assignee) before any other write.
2. Resolve it with the owner. A human-in-the-loop decision is the owner's answer, asked in rounds under "Decision questions"; never answer for them.
3. **Post the owner's answers** on the decision ticket, each round as soon as it's answered: each question with the answer quoted word for word, never a summary, any sensitive data (`profile.md`) left out and marked as left out. A research or task decision posts what the owner said, if anything.
4. **Write it down:** the ADRs and the domain glossary (`GLOSSARY.md`, or the name the project uses), committed to a branch. Research notes go in a research pull request ("Research"), linked from the ticket they answer.
5. **Review it** with the `review-panel` skill's planning review (§8) until a round is clean, and fix what it finds. A decision that changes no ADR or glossary skips this step and step 4's commit (research notes still go in their research pull request), and its checklist says so. A fix that would change what a decision means goes to the owner as a question first.
6. **Only then** record it: a resolution comment, close the ticket, the map's "Decisions so far", unblocked tickets updated, new tickets created and wired. Offer the pull request with its review records, naming anything still open in its body. This order replaces `wayfinder`'s, which records and closes straight after resolving.
7. When every Destination item has its spec and its tickets, close the map as completed.

**The gate.** A map's build tickets wait until every Destination item of that map has its spec and its tickets, so building never starts on half a plan (held items: "Research"). `workflow ready` doesn't apply it; `next`, `start` and the conductor's kick-off do.

**Checklist:** claimed first; every decision the owner's, each round checked, posted as answered and tagged; answers posted verbatim; reviewed until clean, records posted; recorded and closed; map updated; dependents updated; glossary and ADRs committed with a PR offered, research in its research pull request; next ticket named.

## 2. A spec and its build tickets: one spec per session

1. Settle the idea with the owner first, in the same session: `grill-with-docs` (or a map's decisions). Then follow `to-spec`: agree the test seams with the owner and write the spec's draft, citing the decision behind each choice.
   **Post the owner's answers** ("Decision questions"), each round as soon as it's answered: each question with the answer quoted word for word, the seams among them. They go on the item's issue or the map's Destination item (a comment on the map naming it), when there is one. A spec with neither files an item's issue first, so its rounds are posted before the spec is published. Then review the spec's draft with the planning review (`review-panel` §8) until a round is clean, fixing as §1 does, and publish the reviewed text as is (`ready-for-agent`). Each round's spec record goes on the spec's issue (`workflow review-record --kind spec --body`): it names the hash of the spec's body, so an edit after the review makes the spec read as unreviewed again.
   Label the spec `spec` as well, so readiness never mistakes it for a build ticket. A spec for a map's Destination item is linked from that item in the map's body (and its tickets are the spec's sub-issues), so `next` and the conductor can tell which items are specified.
2. Follow `to-tickets`: agree the breakdown (**Agree these**), run the breakdown check ("Decision questions"), then publish build tickets (`ready-for-agent`). Each build ticket has:
   - `## Blocked by` (issue refs, or "None"), written out even when also linked with GitHub's own dependencies, so a blocker closed as not planned is seen;
   - an `Area: <name>` line from the profile's `[areas]`, so the conductor never runs two sessions on one area;
   - acceptance criteria naming their seams;
   - the by-hand checks it will need (a real device, account or service), if any;
   - where its structural lines go: its page, or the overview for a cross-cutting rule; a new module (a new folder of code that no page covers and that held no code before), a full page for the outermost one; a file no page covers, a `Covers:` line in the page named by its folder path (`.tools/lint/check.py`: `tools--lint.md`; root: `_root.md`);
   - `Review: small` if the change should stay within the small threshold and add no endpoint, table, screen or setting (§3);
   - `## Bar`, required in a `run.bar_areas` area ("The bar").
3. Anything only the owner can do (create an account, a key, a domain) is its own issue labelled `owner-task` (or `ready-for-human`), and blocks what needs it.
4. **A change to a protected path** (the profile's `guard.protected_paths`: the kit, CI config, CODEOWNERS, secrets files) is an owner task too, labelled `owner-task`, never a build ticket: a ticket session can't change those paths. `workflow ready` notes a ticket whose body names one ("names protected path … : check it isn't an owner task"), leaving it ready; the conductor lists such tickets at kick-off for the owner to keep or exclude. Paths in fenced code (unless the prose before it asks for a change "to" or "in" it), or after "don't", "do not" or "never" in their clause, aren't noted; when in doubt, a path is noted.
5. **A ticket that fixes a failing or flaky required check** is infra: label it `workflow:infra` as well, so it starts before other tickets. (If its fix is to CI config itself, it is an owner task, as above.)
6. **An issue triaged to `ready-for-agent`** (by `triage` or `start`'s sorting) is a build ticket too: it gets item 2's parts before it gets the label.
7. **Commit what the session wrote:** the domain glossary, ADRs and architecture lines, on their own branch, with a pull request for the owner to merge (with architecture lines, under the spec's tickets' `## Blocked by`). They get the planning review as §1 does before the pull request is offered, with its review records on its commit. Research notes go in a research pull request ("Research"), linked from the spec. They are files in the working tree, and a cloud session's are gone when it ends.

**Checklist:** every input decision used or ruled out with a reason; seams agreed; each round checked, posted as answered and tagged; answers posted verbatim; reviewed until clean, records posted; spec published; tickets agreed, checked, published, wired, each with an area; owner tasks filed (protected-path changes among them); check fixes labelled `workflow:infra`; glossary, ADRs and architecture lines committed with a PR offered, research in its research pull request.

## Decision questions

The questions whose answer is posted as the owner's: a map decision's rounds (§1, through `wayfinder` and `grilling`, which stay unedited), the spec interview (`start`'s Spec step, or `next`), a study's intake and its verdict, posted on its research issue ("Research"), the seams, the questions the planning review's **Fixes** sends once a draft exists (`review-panel` §8), and edits after publishing (`start`'s **Edit the spec first**, and **Add to an existing issue** on a spec). Each follows every rule below, and the skills that ask them (`start`, `next`, `review-panel` §8) follow these rules. Of the checks, a study's intake and verdict get only the one before each round: no end check or re-read until spec #505's open question on it is settled. A quick ticket gets the end check and the "Decided for you" list (`start`), without posted answers. The run charter's questions (`conductor`) get the evidence rule only, with no checks. Routing choices (which step comes next, such as **Build it now** or **Write the spec**) get neither.

Four routing choices in research are each recorded in one line, with the reason and the owner's choice:

1. run or skip a study (the stakes record);
2. the professional choice;
3. after a source changed, one choice with three options: going on, fixing the note or re-running the study;
4. bringing in an old note ("Research", **Old notes**).

Each line goes where the work's rounds are posted: the research issue, or, with none, the item's issue (for a map's Destination item, a comment on the map naming it), the spec's issue or the decision ticket. No other routing choice is recorded.

- **Evidence.** Each recommendation says what it rests on (the file, issue, ADR or answer checked), what it gives up, and what would make it wrong. Where there's no basis to prefer one option, there's no "(Recommended)": lay the options out. The evidence and the checks' findings follow the sensitive-data rule (`profile.md`), left out and marked as left out, before anything is posted.
- **Asked in a message.** A round asked in a message rather than as choices, as `grilling` lays one out (its rounds, its frontier, its "❓" question and its "➡️" line, kept whole and unedited), labels each part, so a recommendation can't be mistaken for a decision already made. Each question is laid out in labelled parts: the question (`grilling`'s "❓" line), worded as a question, then ➡️ **Recommended:** the answer followed by its evidence (*Rests on:*, *Gives up:*, *Wrong if:*), or "➡️ Recommended: none" with why where there's no basis to prefer one, then **Alternatives:** each real alternative, one line each. Never the recommendation as the question's first sentence or a bold paragraph of its own. A round posted on GitHub keeps the same parts: a table with "Recommended" and "Alternatives" columns, or the same labels. A question asked as a choice (`AskUserQuestion`) is unchanged, its recommended option first with "(Recommended)" and its evidence in its description, and so are the run charter's questions (`conductor`). For example:

  > ❓ **Q14 - Urgent: typical or longest?** What counts as urgent: the typical CI time, or the longest?
  >
  > ➡️ **Recommended:** the longest.
  > - *Rests on:* one run that hits the timeout fails CI.
  > - *Gives up:* more urgent flags.
  > - *Wrong if:* one slow run shouldn't count.
  >
  > **Alternatives:** the typical time, the same measure as the 10-minute threshold.
- **"Yes to all"** answers only the questions with a recommendation; ask any other again on its own. A finding about the owner's own words (an answer they typed, not a recommendation they accepted) is asked on its own.
- **Each round** is posted as soon as it's answered, not only at the end. It goes where the owner's answers go: the decision ticket (§1), the item's issue or the map's Destination item (§2); a study's intake and verdict go on its research issue; the breakdown check's rounds and an edit after publishing go on the spec's issue. A spec with none of these files an item's issue first. The post carries each question, its recommendation and evidence, the checks' findings, and the owner's reply quoted word for word, tagged **accepted recommendation** or **the owner's own words**. A replacement or narrowing the owner confirmed is a plain line ("answer 34 replaces 7: confirmed").
- **The checks.** The read-only `planning-checker` agent reads, and marks each finding **ask** (it changes what an answer means: the owner decides) or **fix** (wording, a fact or an omission: the session makes it). It reads each round's recommendations before the round is asked, except a check's own rounds (the end check's and the breakdown check's), and never repeats a round's own check. After the last round, before the spec or a map decision's ADR is written, it reads all the answers together (the end check). The end check's **ask** findings come back as one short round, with **Leave them open** among its options. Then it reads, once, only what that round changed, against the rest (the re-read), and stops. Each round sent after a draft exists gets one re-read against all earlier answers.
- **The breakdown check.** After **Agree these** (§2), `planning-checker` reads the breakdown against the spec: each decision and acceptance criterion in exactly one build ticket, owner task or edit to an existing issue (criteria every ticket carries, such as the changelog note and the full suite, are left out, and so are decisions that build nothing: out of scope, or something left unchanged); each `## Blocked by`; each `## Bar`, where the spec gives one. Only wording is a **fix**; its **ask** findings are answered before the tickets are published. Its re-read's **ask** findings are asked too, as one more short round with no read after it. A finding left open keeps the tickets it affects out of `ready-for-agent`, with the finding in their bodies.
- **Each read's fixes** are listed where the owner can object: in the post of the round that follows the read; with no round after it, in a comment on the same issue straight after the read, with what it leaves; on a quick ticket, above **Publish it**.
- **What's left** after a last read goes into the spec's Further Notes as open questions before it's published, or a comment on the spec's issue listing them after; for a map decision, its resolution comment; on a quick ticket, its `## Decided for you`, marked open. It is never only in the session's closing choices. What's left is what was unanswered or left open, and a last read's **ask** findings: a re-read's **ask** findings are never asked, except the breakdown check's. A last read's **fix** findings are made.
- **Not the planning review.** These checks (before each round, the end check, the re-reads and the breakdown check) aren't `review-panel` §8's planning review: each reads once and re-reads once, never in rounds until clean, and posts no spec record. Once a check's **ask** round is answered or left open, nothing it found stops the publish (a breakdown finding left open keeps its tickets out of `ready-for-agent`), unless #363's spec changes what blocks these checks.

## Research

All research, studies and fact notes alike, lives in the repository, in `docs/research/<topic>/`, and reaches the base branch through a **research pull request** of its own, on a branch named `claude/research-<topic>`: a study's note, a map's research tickets' notes and the `research` skill's. No new note goes on a `research/*` branch.

- **The order.** A study runs from the intake to the verdict: the intake (no question cap), then the panel's research, then the verdict (build it, prototype first, or stop). Grilling follows build it, or the `prototype` skill on prototype first, and stays uncapped, starting from the study's findings and its ranked questions. Stop ends the work there, with no grilling. For a new project on a map, the intake and the panel run before charting's first step. The study's research issue is linked from the map's Notes, never made one of the map's children, since map tickets carry only `wayfinder:` labels.
- **A brand-new project** (no code of its own) is always recommended one study, on its first item offered one; every later item takes `start`'s offer as in any project (an internal change gets none), its map's Destination items, where the map's Notes link a study's research issue, only once that study's verdict lets them go on, never on stop (`start`'s **Offering a study**). Its map's open decisions wait for that verdict too: on prototype first, the prototype comes before them; on stop, none is offered, and the map is closed as not planned with them, linking the verdict, never as completed (§1 step 7) (`next` §1, "A map").
- **The overrides.** These override three vendored skills, which stay unedited, as §1 step 6 overrides `wayfinder`'s order:
  - `wayfinder`'s `research/<name>` branch, pushed with no pull request and never merged: a research ticket's note goes in `docs/research/<topic>/` through a research pull request instead.
  - The `research` skill's "where the repo already keeps such notes": its note goes in `docs/research/<topic>/`.
  - `to-questionnaire`'s "in the current directory": a questionnaire for a finding goes in its topic's `docs/research/<topic>/`.

  `grilling` stays unedited too.
- **Fact notes from background subagents** (a map's research tickets, resolved in parallel). Each subagent writes in its own worktree, on its note's `claude/research-<topic>` branch, so a note never lands in another branch's working tree. A subagent can't start another agent, so the session that started them opens each note's research pull request and runs its research check.
- **The note.** One note per topic, updated in place (git keeps the old versions), in the layout the `study` skill shows. Its header is three lines at its top: `Status:` (`current`, or `superseded by <link>`), `Last checked:` (a date, for information only) and `Issue:` (`#<n>`, its `research` issue). A fact note with no issue to name (the `research` skill run on its own) gets a `research` issue filed for it. Agents read only notes marked `current`: `workflow research notes` lists them.
- **Old notes** on `research/*` branches, or merged without the header, stay where they are until used. When a session relies on one, it offers to bring it in, with the header, saved copies, fingerprints and the research check, through a research pull request (a routing choice, recorded in one line: "Decision questions"). The kit's own notes go in its `docs/research/` too.
- **The research check,** for every research pull request, studies and fact notes alike: one pass each for the research check and the look, never in rounds until clean.
  - The research check: before the note merges, one read-only `research-checker` reads each claim citing a saved copy against it, whatever its label, facts only (a claim cites a saved copy by its path, or by the address its `Source:` line names); a claim or finding citing none is never called wrong for having none, whatever its label and whatever it rests on; a line linking a page with no saved copy, or a fact note's claim citing no source, is a fault of the note on its own, which makes the result not clean as a wrong claim does. The checker posts nothing, so the session posts its result as one comment on the pull request: first the research record (`workflow review-record --kind research --round 1 --reviewers research`), naming the commit it read and whether it was clean, then the claims it found wrong and the faults. The record comes first because the record reader stops at the first code fence, and a claim may quote one.
  - The look, short for the look at a fix: the session fixes the claims and faults the research check found, then a fresh `research-checker` reads the lines changed since the research check and the claims and faults it listed. A listed claim or fault whose line didn't change counts as still wrong. The session posts the look's comment and research record (`--round 2`) the same way. A claim still wrong, or a fault still there, gets the unconfirmed mark at the end of its line, and there is no further round.

  How the research check's record, the look's record and the mark count at merge is §4 item 4's (**A pull request of research notes**), so §4 stays the merge rule's one source.

- **A finding that needs a professional** (the law, a regulation, a safety rule). The session flags it and the owner chooses each time, before the note's research check, so its open mark, questionnaire or link is in what the check reads. It is a routing choice, recorded in one line ("Decision questions"), with three options:
  1. **Research it ourselves:** a focused second study by fresh agents. They read only primary texts, each conclusion quotes its clause, and a skeptic argues the other reading; the result is labelled "researched, not confirmed by a professional". It is its own note, in a topic folder of its own, through a research pull request of its own with its own research check, tracked by a research issue of its own, filed when the owner chooses it and named by the note's `Issue:` line. It has no intake and no verdict. The main note links to it and marks the finding open. Once the second note merges, a research pull request updates the main note's mark to point to the result, with its research check, and closes the second study's issue (`Closes #<n>`). Its token record carries the second-study marker, `study=second` (the `study` skill's section 3).
  2. **Ask a professional:** a questionnaire, written as `to-questionnaire` writes one and saved in `docs/research/<topic>/`, with an owner task (`owner-task`) that links it.
  3. **Leave it open:** listed on the research issue, and marked open in the note.

  - **What waits:** only what rests on the professional's answer. The verdict and grilling go ahead, and the finding is marked open on the research issue.
  - **Holding back:** each item that rests on the answer lists the owner task under `## Blocked by`: the item's issue, its spec and the build tickets (`workflow ready` already holds those). A map's Destination item has no issue, so a `Blocked by: #<n>` line goes beside it in the map's body: the session that files the owner task writes it beside each Destination item that rests on the answer, or, when the task comes before the map (a new project's study), charting writes it (`wayfinder` stays unedited: this overrides its charting). `workflow status` doesn't read that line: `next` and `start` do, and skip the item while its task is open. A Destination item's records go where the `study` skill's section 5 says.
  - **The gate** (§1): a Destination item with a `Blocked by:` line is left out of the gate whether its task is open or closed, and the line stays. So the map's other build tickets can be built while it is held, and once its task closes, only the held item's own tickets wait for its spec and tickets.
- **The source check,** whenever a decision relies on a note: a recommendation's evidence cites it, or the build of a session building a ticket follows it. The session first runs `workflow research check --note <note> --fetch` (the `study` skill's section 1), which says for each key source:
  - **Unchanged:** nothing to read, and no model tokens spent.
  - **Changed:** the model reads only the changed paragraphs `check` gives (each new one's live text and each one gone, each with its hash) and recommends one of three: go on, fix the note, or re-run the study. The owner's choice is a routing choice, recorded in one line ("Decision questions").
  - **Can't fetch:** for a small decision, one line in the evidence says so; for a high-stakes one, the owner is asked. Whether a decision is high-stakes is the model's judgement, made for that decision.

  A session building a ticket:
  - **Attended:** the owner chooses after a changed source, as above, and is asked about an unfetchable one for a high-stakes decision. After "fix the note" or "re-run", the build goes on with the decision taken on the current note, recorded in the pull request.
  - **Unattended** (a ticket session in a run): a change that doesn't touch the decision, or a small decision, is noted in the pull request, and the session goes on. A high-stakes decision follows the charter's `open_decisions`: decide-and-record takes the safest choice, as the briefing's line for research-source decisions says, and records it in the pull request; set aside stops the ticket at `needs-human`.
  - **What it goes on with,** after a change that touches the decision: the current note, with the changed paragraphs quoted in the pull request; under decide-and-record, the safer of the note and the live text; after the owner chose "fix the note" or "re-run" on a stopped ticket, the current note, except under decide-and-record, which still rests on the safer of the two, as Choosing once says below.
  - **Its lines:** its can't-fetch line and its routing line go in its pull request and on the build ticket. When it stops at `needs-human`, its line there names the note, the source's link and the changed paragraphs' hashes from `check`, new and gone.
  - **Quoting a source:** changed paragraphs quoted in a pull request, on a build ticket or on a research issue leave out personal details and anything matching the profile's `[sensitive].patterns`, as saved copies do, and every HTML comment (`<!-- … -->`), the kit's markers among them, each marked as left out (`check` already leaves out the patterns; personal details and HTML comments are the session's to leave out).
  - **Choosing once:** when the owner answers a ticket stopped on a changed source, the conductor posts the answer as an "Owner chose" line on the build ticket and on the open research issue for that note and source (the `conductor` skill's "When the owner answers"). A later session on that ticket follows it only when `check` reports the same paragraphs for that source, new and gone, by their hashes as a set; anything new is a new choice. The planning session that takes the research issue reads it as the owner having chosen. Only a line with the "Owner chose" marker and the agents' marker, posted by an account with write access, counts, as hand-off comments do, and only when the comment holds the fixed shape below and nothing else: the line, then the two markers, each once and on a line of its own, never inside a code fence. The one exception is a cloud session's footer, once, at the very end (a blank line, `---`, then `_Generated by [Claude Code](https://claude.ai/code)_`, which a Claude Code cloud session's GitHub tools add after every post), with nothing else before it but the fixed shape. A session's own routing line never counts as the owner's, never carries the marker, and neither does the stakes line, which has its own. Under decide-and-record, a matching line settles the choice, and the build still rests on the safer of the note and the live text. An answer about a source that can't be fetched has no hashes to match, so it doesn't count for a later session, which runs the check afresh and, if it still can't fetch, stops (or decides) again. The line's one fixed shape, the choice (go on, fix the note or re-run the study), the note, the source's link and the hashes, `none` where there are none:

    ```markdown
    Owner chose: fix the note. Note: `docs/research/booking-ahead/note.md`. Source: <https://example.com/help/booking>. New: ece1eadaed507719006ab2e8a550d9988c171b7d9f16a36c3d2825323dac7d55. Gone: 4301a2050cf762c2ae5567611ac08bb487eaba2d7190b6eba3712bfe6cdb6ed0.

    <!-- workflow:owner-chose -->
    <!-- workflow:agent -->
    ```
  - **A research issue** (labelled `research`, naming the note, the source's link and the hashes) is filed, or an open one for the same note and source is commented on, only when a note is to be fixed or re-run, or when no owner was there to choose (unattended, with a change that touches the decision or a source that can't be fetched). An attended "go on" files nothing. `start` lists it, and its "Carry on" row takes it: the research pull request that fixes the note or re-runs the study closes it (`Closes #<n>`); when no note changes (the owner chose to go on, or the claim was right), the planning session closes it with its routing line.

  A Destination item's routing lines go where the `study` skill's section 5 says.
- **Fixing a wrong note.** Whenever a session finds a claim in a note wrong, the note is fixed in a research pull request, with its research check. A session building a ticket can't open a second pull request: it files an issue labelled `research`, naming the wrong claim and its evidence, and mentions it in its own pull request; when an open `research` issue already names the same note and source, it comments there instead. `start` lists it, and a planning session takes it: it runs the source check and the owner's choice, unless the owner already chose (an "Owner chose" line on it that matches, from an account with write access, as Choosing once says).

## The bar

A build ticket's `## Bar` says where the reviewers' hunt stops: what the change must handle, what it does when it can't be sure (fail closed), and the limits it accepts, each with its backstop if any. A spec may give one for its tickets. A ticket may carry one, and one whose area is in the profile's `run.bar_areas` must: `workflow ready` notes such a ticket with no `## Bar`, leaving it ready, as it notes a protected path. For example:

```markdown
## Bar

- Must handle: a note saved with an empty title, and two saves of one note at once.
- Fail closed: when it can't tell which save is newer, it keeps both and says so.
- Accepted limits: notes over 1 MB aren't checked (backstop: the server refuses them).
```

## 3. Building: one ticket per session

Follow the `build-ticket` skill, one ticket at a time. When the person typed `implement` or `implement-spec`, build with `build-ticket` all the same, ticket by ticket, instead of those skills' own steps (no commits straight to the current branch, no parallel builders on one branch). In short:

1. **Claim** it; read the ticket, its spec, the project's rules, the architecture documents `workflow index reads` prints for the files it expects to change, the pages list (`workflow index pages`) and the notes the briefing points to.
2. **Build** it: `tdd` at the spec's seams; the typecheck and single test files as you go; the full suite at the end.
3. **Review** with the `review-panel` skill: Standards, Spec, Correctness (with a security review for an auth, upload, payment or API change) and, when the explorer isn't `none` (the briefing's in a ticket session, else the profile's `ui.explorer`) and the change touches a screen, an endpoint or a command, the explorer, in parallel. Verify each finding, fix the real ones with a test, answer the rest with a reason. Repeat until a round is clean, at most the briefing's review rounds in a ticket session, else the profile's `run.review_rounds`; a short Correctness pass then covers any commit made after the last round, up to the **pass cap**: at most the briefing's pass cap in a ticket session, else the profile's `run.review_passes`, after which the owner decides (a cap of `until-clean` is none: passes until one is clean, within the run's end time). The exception is a merge of the base that leaves the pull request's own changes identical, which needs CI only: after pushing a merge of the base, run `workflow merge-check` (in a ticket session, with the briefing's flags) and run a pass only when it asks for one. Each round and each later Correctness pass posts its review record on the pull request (`workflow review-record`): the commit it covered, who reviewed and whether it was clean, whatever it found.
   **Under the rule for build reviewers** (`review-panel` §10), a review never stops to ask the owner, except where `build-ticket` §3 or `review-panel` §3 hold the ticket for them. Build reviews follow it in attended work always, and in a ticket session when its briefing has a "Findings:" line. Where the rule differs from the above, it wins:
   - **What blocks.** A finding blocks only with a reproducer, a concrete case that fails; without one it is a note. A real defect outside the change, or a lesser one on lines an earlier review already covered, becomes a ticket to fix it, filed as `build-ticket` §3 says. A review is clean when no finding blocks.
   - **The fixer.** A fresh `fixer` agent makes each review's fixes, round 1's included, each starting with a failing test from its finding, and preferring a fix that removes a case over one that adds an exception. From the second review, reviewers check what changed since the last one and what it reaches.
   - **The bar.** A ticket's `## Bar` ("The bar") says where the hunt stops: a gap it accepts is a note.
   - **A part that keeps blocking.** When the same part of the change blocks in two reviews in a row, `workflow merge-check` says what comes next (`mechanism_repeats`), and the session does it. The part takes the safe fallback the bar describes; or it is split out to a ticket of its own, filed first with the acceptance criteria that need it, and the pull request merges without it; or, when neither is left, its findings are fixed as usual and the review goes on. A part is split only once, and a security problem the change adds is fixed, never split out.
   - **No pass cap.** Correctness passes follow the last round until one is clean. In a run, the end time is the only limit (§5). In attended work, the session prints one progress line at each review that isn't clean, and after 10 such reviews in one session it stops: it leaves the hand-off on the pull request and labels the ticket `workflow:carry-on`, which `start` lists with a **Carry on** choice. "Carry on #<n>" in a fresh session goes on, with a fresh 10.
4. **Pull request** to the base branch: "In plain words" first (what changes for you, how to try it, what could go wrong), then `Closes #<n>`, what was built, how it was tested, the findings table, the decisions taken.
5. **Green and merge** under the merge rule (below), or leave it for the owner in attended work.

**The small review,** on a ticket marked `Review: small` (§2) whose diff stays within the small threshold (the briefing's in a ticket session, else the profile's): one round of Correctness, with the security review and the explorer where they apply, then Correctness passes under the pass cap (under the rule, until one is clean), with no further rounds (`review-panel`, "The small review"). It is allowed in attended work always, and in a run when the briefing says the small review is on, a 1-round run included. `build-ticket` measures the diff before reviewing; past the threshold, the ticket gets the full panel (the light review in a 1-round run), and the PR body says the diff overruled the mark. The person can still ask for a light review or the full panel instead, and removing the line opts the ticket out.

**A light review,** asked for as "build #12 with a light review" (or "quick build #12"), and used when the briefing's review rounds are 1 on a ticket that doesn't get the small review: one full-panel round without the explorer, then Correctness-only rounds for its fixes, at most 2 more, each posting its record (`review-panel`, "The light review"); under the rule, Correctness passes then follow until one is clean. It is never chosen for the person, and the merge rule stands unchanged.

**Checklist:** blockers closed and spec read; each acceptance criterion met with its test; typecheck and full suite pass; review rounds until clean; every finding fixed or answered; PR opened with the findings table; merged under the rule (or left for the owner); notes for the next tickets posted.

## 4. The merge rule

A pull request merges only when all of these hold on its current head:

1. **Every required check is green** (`ci.required_checks`). A check the run's charter waives counts only if its log shows it was **killed, not failed** (the profile's `ci.killed_markers`: exit 143, runner shutdown, cancelled, never started). A real test failure always blocks. Waivers need `merge.mode: session`, since GitHub's auto-merge can't tell killed from failed. `workflow merge-check` applies them from `--charter` and `--check-logs`, never in an attended session. Waivers don't apply with the merge queue on: every merge then goes through the queue, and only a direct merge could take one.
2. **The full suite passed locally on that exact commit**, posted on the PR by `workflow evidence --base-ref origin/<base>`: the command, SHA, counts, duration, and no fewer tests than the base branch (with the profile's `commands.select_suites`, the suites the PR's files need, on both; where this report is required, only the full suite's counts). Required when a check is waived or the profile says `ci.none`; recommended always. `workflow merge-check` then reads the report's first line for the head, from an account with write access. When the base branch's own suite doesn't pass, the report says the count wasn't compared; the PR may still merge, and the conductor opens an infra ticket for the base.
3. **The branch is level with the base, or met by the merge queue where the ruleset requires one.** Without a queue, whoever merges second merges the base in, and CI and the suite run again, with a review only where item 4 needs one; a queue tests each pull request on the latest base itself.
4. **The reviews are clean**, and any commit after the last round had its Correctness pass, except a merge of the base that leaves the pull request's own changes identical (context lines included, by the `diff` hash on the review records): the last counted review carries over to it, with its result, clean or not, and it needs CI only. A round that wasn't clean needs another round, unless it was the last allowed one (§3 step 3): then a clean Correctness pass on the head lifts its findings, and no further round is added. Under today's rule, passes stop at the pass cap (§3 step 3): where one more would be needed past it, the pull request waits on the owner; with `until-clean` there is no cap. A review recorded under the rule for build reviewers (a `rule=2` record, written by `workflow review-record --findings`) is clean only when it reports no finding marked blocks (a finding kept after a contest is one; a note or a ticket to fix it never makes it unclean), and has no pass cap, whatever the briefing or the profile says; the round limit stays. When the same part has a blocking finding in two such records in a row, `workflow merge-check` names what the session does before the next review (`mechanism_repeats`, §3 step 3), never the owner. On a pull request with records under both rules, the latest counted record's rule decides (latest by the pull request's commit list, the head always the newest, then by posting, so a record posted late for an older commit doesn't decide it). A pass on a merge of the base after a clean review, needed only because the lines around the PR's own changed (the same `lines` hash), doesn't count toward the cap (a pass that rechecks open findings always counts), and is asked for even at the cap. A review in which no counted round ran Spec (the small review) counts only while the diff is within the small threshold (the profile's `run.small_max_lines` and `run.small_max_files`, counting files outside tests): past it, a full-panel round is needed, allowed past the round limit; within it, a round that wasn't clean counts as the last allowed one, and so does that full-panel round.

   **A pull request of research notes** (every file under `docs/research/`, a rename's old path included): a pull request whose files are all research notes counts its research check record as its clean review; items 1 to 3 still apply, and so do #30's conditions. Its research records (`workflow review-record --kind research`: round 1 for the research check, round 2 for the look at a fix, each from an account with write access, for a commit of the pull request) are its reviews, and its latest counted one decides, latest as above; review rounds and passes don't count there, and research records count nowhere else. What changed since a record is judged on the pull request's own changes: when they are the record's (its `diff` hash), after a merge of the base or a change taken out again, nothing did. The research check, clean, with no change since, is its clean review; not clean, or with any change since, it needs the look at a fix, whose record counts the same way. The look, clean, counts with no change since or only marks added; the look, not clean, counts once the net change since adds only marks, at least one. The mark is ` **(unconfirmed)**`, added at the end of the line holding a claim the look still found wrong. Only marks after the look: anything more than marks after it, judged on the net change, makes it not ready until that change is taken out, or moved to a new research pull request.

This section is the merge rule's one source; skills and briefings point here rather than restate it.

`workflow merge-check` is its one implementation, run by the `merge-check` skill and the conductor. Each of its rules names the item above, or #30's condition, that it implements (an open pull request that isn't a draft and has no conflict, no open review threads or outstanding "changes requested", a try-it link that built, and the owner's review for kit and CI files). A test fails when this list and the command's rules differ.

Merging is the owner's in attended work. A planning pull request (a map decision's or a spec session's ADRs and glossary) that the owner merges by hand relies on the review made before it was offered (§1, §2): no check enforces it. In an unattended run, merging follows the charter's `merge.mode`. With "up to date" (no merge queue): GitHub auto-merge behind the ruleset (the session or the conductor keeps the branch up to date until it merges), the session merges with a merge commit (`session`), or nothing merges unattended and the PR waits for the owner (`owner`). In `auto-merge` mode with "up to date", when GitHub refuses to enable auto-merge because the PR is already mergeable (clean), whoever tried (the session, or the conductor) checks this rule again at that moment and, if it holds, merges with a merge commit. With the merge queue on, the modes keep their names and nothing merges directly: a pull request is queued, pinned to the head `workflow merge-check` said `ready` for, and GitHub merges it once its group passes. In `auto-merge`, GitHub's auto-merge is never armed, and whoever first sees `ready` (the ticket session, or a conductor check-in) queues it; in `session`, the ticket session queues it, pinned, after its own final `merge-check` says `ready`; in `owner`, nothing is queued unattended. The ticket session queues each head once and stays with its pull request until it merges; every re-queue after a drop is the conductor's (`charter.md`, "A pull request in the merge queue"). The conductor never merges a change to a protected path itself: it goes to the owner. With the merge queue on, these rules are checked when the pull request is queued: a request made after that (changes requested, a new review thread) doesn't stop the merge.

## 5. Unattended runs

Follow the `conductor` skill. The conductor never builds tickets itself: it asks the owner the kick-off questions once (the **run charter**, `charter.md` in the kit's docs), then hands each ready ticket to its own session, checks in, keeps PRs moving to merge, and reports. A ticket named to the conductor ("build #12", "implement #12", "let's work on #12") becomes a run scoped to it, or during a run the amendment "also #12": a ticket session builds it. What it may do outside the repo is exactly what the charter grants, logged in the run's ledger.

**The never-list.** A ticket session changes only its ticket's code, tests and docs, on its own branch. The owner keeps these to themselves, and the guard hook and the GitHub ruleset back it up:
- deploys and releases;
- cloud settings, secrets, accounts, DNS and payments;
- the base branch (only pull requests reach it), and history (no force-pushes);
- protected paths: the kit, CI config, CODEOWNERS, secrets files;
- the test suite's reach: no test is skipped, disabled or focused away.

**Posts.** Every comment, issue and PR body an agent posts (the conductor's and every ticket session's) goes out under the owner's GitHub account. Each ends with `<!-- workflow:agent -->`, so the owner's own words can be told apart from agents' (`charter.md` §4); the guard refuses a post without it in ticket and conductor sessions.

**Each ticket session** follows "Building" with these differences:
- it stays within the never-list above;
- it first writes its briefing to `.workflow/briefing.md` and checks it with `workflow briefing verify --file .workflow/briefing.md`; its first comment on the ticket quotes the line that prints (`Briefing <hash> intact`), so the conductor sees the briefing arrived intact;
- a check that needs a real device, account or service is built against the spec's fakes and added to the run's by-hand issue as a checkbox, never faked as done;
- a decision the ticket leaves open is taken as the charter says (`open_decisions`) and recorded in the PR;
- if CI is still red after three fix attempts, the review reached its pass cap (with the open findings in the PR body; only under today's rule), or the ticket can't be built as written, it labels the ticket `needs-human`, says exactly why on the ticket and the tracking issue, and stops;
- **under the rule for build reviewers** (its briefing's "Findings:" line), there is no pass cap: the run's end time is handled as `charter.md`'s "The end time" says, and the tickets the session files join the run as its "Tickets filed during the run join it" says;
- **the claim label:** when its ticket ends (merged, `needs-human` or stopped) the session always removes `workflow:in-progress`, and on `needs-human` also `ready-for-agent`; the conductor removes leftovers at its next check-in;
- when its ticket ends it fires the conductor's wake routine named in its briefing, with "#<n> merged in #<PR>", "#<n> needs-human" or "#<n> stopped"; if that fails, it says so in its final note and carries on;
- it ends every turn with `WORKFLOW-STATUS: done | waiting | needs-human | stopped` (`waiting` while CI runs with a check-in scheduled); `done` includes the checklist.
